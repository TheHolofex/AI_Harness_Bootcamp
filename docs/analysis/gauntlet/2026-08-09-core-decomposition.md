# Gauntlet Decomposition — Reformation Core Skeleton

Date: 2026-08-09  
Scope: core structure, sequence, learning objectives, and performance-evidence contracts only

## D1 — Course identity and boundary

**Input:** target audience, field survey, O01/O11/O12.  
**Output:** one stable course promise; explicit user/operator/builder boundary; common-core versus advanced-qualification rule.  
**Invariants:** nondeveloper completion; vendor neutrality; fixed workflow is highest mandatory machinery.  
**Failure modes:** calling advanced agent architecture “core”; treating no-code as low conceptual complexity; marketing breadth without a performance claim.  
**Seam:** feeds every objective and prerequisite. If wrong, all later modules can be individually sound and the course still serves the wrong role.

## D2 — Program learning-objective system

**Input:** professional skill rubric, course promise, O03/O09/O10.  
**Output:** ten observable program outcomes, each with performance evidence and one owning module.  
**Invariants:** no objective without observable evidence; no duplicated primary owner; foundations and responsible release remain practical.  
**Failure modes:** topic lists instead of performances; one objective split across several modules; mechanically uncheckable claims.  
**Seam:** objective-to-module ownership ledger.

## D3 — Sequence and prerequisite graph

**Input:** objectives, guided-to-transfer progression, 24–35-hour budget.  
**Output:** contiguous module sequence no larger than ten, with one primary objective per module and explicit prerequisites.  
**Invariants:** first value ≤60 minutes; guided precedes independent; fixed flow precedes complexity selection; evaluation precedes capstone transfer.  
**Failure modes:** setup before value; diagnosis before a learner has a system model; advanced machinery on the capstone critical path; circular or hidden prerequisite.  
**Seam:** evidence from one module must be sufficient—not merely mentioned—for the next.

## D4 — Practical-work and workplace-surface coverage

**Input:** program outcomes and O06/O07.  
**Output:** minimum three surfaces—research/source, communication, structured-data/batch—assigned once across the core, each with a named artifact and check.  
**Invariants:** practical work serves the module objective; scenario breadth does not create extra modules.  
**Failure modes:** artifact neutrality that produces no assured workplace fluency; duplicated exercises; product-tour creep.  
**Seam:** scenario/surface ledger to module practical-work field.

## D5 — Evidence, failure, and handoff contract

**Input:** O08/O10/O13/O14/O15.  
**Output:** one evidence bundle per module with independent evidence, changed/adversarial condition where appropriate, failure/HOLD behavior, scope statement, and handoff.  
**Invariants:** producer self-assessment never releases material work; simulation is labeled; clean session and independent person are separate.  
**Failure modes:** evidence bureaucracy; calibration dominating practical work; a warm pass counted as recovery; missing evidence silently waived.  
**Seam:** common module manifest fields and capstone recipient rubric.

## D6 — Responsible-release objective

**Input:** NIST/OECD/DigComp/EU concerns and O09.  
**Output:** one contextual release decision covering privacy/security, IP/copyright, fairness/bias, transparency/disclosure, affected-person impact, and accountability.  
**Invariants:** concerns are evaluated when applicable; no universal legal answer; safety cannot be detached from the work artifact.  
**Failure modes:** checklist theater; security-only framing; generic ethics lecture; compliance claim.  
**Seam:** release rubric used by direct work, tools, evaluation, and capstone, owned once in the responsible-release module.

## D7 — Time, practice, cost, and grading budgets

**Input:** O05/O16/O19.  
**Output:** module time/practice declarations, summed arithmetic, line limits, spend and judge-time budgets.  
**Invariants:** 24–35 facilitated hours; ≥60% practice; ≤10 modules; ≤900 authoritative module lines.  
**Failure modes:** hidden homework; impossible scoring; duration added after content; quality claims without measures.  
**Seam:** module manifests to course-map rollup.

## D8 — Degraded and scale behavior

**Input:** O18 and cohort assumptions.  
**Output:** course-level rules for unavailable model/tool/fixture, inaccessible surface, simulation, test-out, and 200-learner delivery.  
**Invariants:** objectives and claim labels do not change; missing proof produces bounded alternate evidence or HOLD.  
**Failure modes:** discussion relabeled performance; hidden-case leakage; instructors improvising different rubrics at scale.  
**Seam:** course-level delivery contract, not duplicated module prose.

## Single riskiest seam

**D1 → D2: converting a broad “AI harness operator” identity into a finite objective boundary.**

This seam determines whether Modules 08–10 are recognized as useful but advanced system-operation qualifications or remain mandatory merely because they can be run without code. A failure here propagates to sequence, time, nondeveloper accessibility, and capstone prerequisites. The winning implementation must retain complexity-selection judgment in core while removing full persistent-state, adaptive-loop, and multi-agent operation from common completion.

## Scout-tier implementation choice

Only one implementation is required at Scout tier. Use the **common-core plus operator-qualification** model ranked first in the frozen Reference. The conventional all-00–12 linear path loses because it fails O04, O05, O11, and O12; the scenario-spiral model remains a delivery option but does not by itself repair the role boundary.
