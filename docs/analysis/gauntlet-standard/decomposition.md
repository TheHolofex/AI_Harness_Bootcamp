# Standard Gauntlet Decomposition — Reformation Core

Date: 2026-08-09  
Scope: identity, outcomes, sequence, prerequisites, work surfaces, evidence contracts, budgets, degraded behavior, and transfer

## D1 — Occupational boundary

**Input:** target learner, field survey, S02/S12/S13.  
**Output:** one course promise and a four-way responsibility split: learner, harness operator, adapter, builder.  
**Invariants:** common completion requires no implementation; fixed workflow is highest mandatory machinery.  
**Failure modes:** “no code” used to smuggle agent construction into core; adapters pre-decide judgment; user skill flattened into product operation.  
**Seam:** constrains every learner action and capstone claim.

## D2 — Program outcome ledger

**Input:** need statement, field competencies, S04/S05.  
**Output:** ten observable outcomes with one owner, evidence, and explicit claim boundary.  
**Invariants:** task–knowledge–risk–skill integration; no topic-only outcome; no duplicated owner.  
**Failure modes:** compound outcomes whose branches cannot both pass; one module teaches what an earlier module already claims; transfer replaces component outcomes.  
**Seam:** objective string and claim ID shared by objective ledger, map, and module manifest.

## D3 — Responsibility-before-release spine

**Input:** S07/S10/S11 and modules that accept or release work.  
**Output:** minimum responsibility screen before any consequential release; one full contextual release/tool gate later; correct refusal and selected operation scored separately.  
**Invariants:** rights, affected people, disclosure, authority, and human owner appear before release; `no-use/no-tool/no-release` can be correct.  
**Failure modes:** early unsafe release; six-box checklist; correct refusal fails because operation did not occur.  
**Seam:** common screen product from Module 00 consumed by 01–03; full decision product in Module 04.

## D4 — Prerequisite product graph

**Input:** all module first actions and evidence bundles, S14/S20.  
**Output:** explicit `Consumes` and `Produces` tokens; each consumed product exists earlier or begins `VERIFY:` at the consuming module.  
**Invariants:** no orphan, circular dependency, unsupported bypass, or handoff-only promise.  
**Failure modes:** snapshot/restore appears without proof; alternative route lacks baseline; `HOLD` disappears at capstone.  
**Seam:** exact stable product token, solved once and reused.

## D5 — Evidence and qualification contract

**Input:** S09/S15/S19/S20/S21.  
**Output:** one bundle per module, protected/independent decisive result, explicit partial versus complete claim, course-outcome ledger, clean-session and person gates.  
**Invariants:** producer cannot edit/bypass/select check; localization is not recovery; capstone cannot erase missing POs.  
**Failure modes:** file presence becomes competence; bounded `HOLD` becomes pass; fresh model substitutes for person.  
**Seam:** each module's `Claim result` and the capstone qualification ledger.

## D6 — Nondeveloper error-improvement boundary

**Input:** observed run corpus, S12/S16.  
**Output:** learner specifies a mechanically decidable predicate, configures and validates it in a supplied protected control; adapter owns new implementation.  
**Invariants:** arbitrary semantic failures are not forced into deterministic rules; protected custody stays separate.  
**Failure modes:** hidden coding requirement; instructor builds a bespoke check inside the timebox; learner receives implementation credit.  
**Seam:** predicate specification to supplied control schema.

## D7 — Deterministic versus stochastic evidence

**Input:** fixed workflow and change comparison, S17.  
**Output:** exact delta scoped to deterministic outer state; material probabilistic output gets predeclared repetition, paired controls, uncertainty treatment, or exclusion.  
**Invariants:** one lucky run cannot establish method improvement; repetition policy predates results.  
**Failure modes:** ordinary output variance appears as change; exact fields demanded from stochastic generation; underpowered comparisons overclaim.  
**Seam:** evaluation policy owned once in Module 08 and invoked by Module 07 when its model station affects the decision.

## D8 — Composed adversarial boundary

**Input:** context precedence plus tool authority, S18.  
**Output:** one protected negative combines instruction-like untrusted content and a bounded available action; expected result is no unauthorized action, authority expansion, or hidden side effect.  
**Invariants:** isolated context and tool tests do not substitute.  
**Failure modes:** prompt injection reaches an authorized tool despite each component passing alone.  
**Seam:** Module 04 owns the combined release/tool gate using Module 03's source-as-data control.

## D9 — Time, cost, scoring, and scale honesty

**Input:** module manifests and S06/S23/S26.  
**Output:** unambiguous included practice; provisional budget language; required pilot telemetry and agreement methods; 20/200 policy trace.  
**Invariants:** declarations are not measurements; scale cannot weaken rubrics or transfer.  
**Failure modes:** 30+20 interpreted as 50 hours; 15-minute scoring drives file checking; hidden-case leakage; recipient capacity omitted.  
**Seam:** one course-map budget table and one evidence-status table.

## D10 — Skeleton parsimony and integrity

**Input:** S24/S25.  
**Output:** ≤10 module skeletons, one authoritative objective/map/guide system, static integrity test, explicit deletion ledger.  
**Invariants:** every file and module serves named criteria; implementation prose stays out.  
**Failure modes:** duplicate record systems; keyword-oriented text added only for tests; deleted prerequisite concept not restored.  
**Seam:** authoritative-file manifest.

## Single riskiest sub-problem

**D4 — prerequisite product graph and qualification closure.**

A course can have strong individual modules and still make an invalid qualification claim if a consuming module relies on an unproduced capability or if capstone completion launders prior `HOLD`s. The current skeleton exhibits both: Module 05 consumes snapshot/restore without a prior gate, Module 08 offers a Module 06 bypass without a preserved restorable baseline, and Module 09 allows bounded `HOLD`s without a final outcome-closure rule.

At Standard tier this seam is implemented once through explicit `Consumes`/`Produces` contracts and a final program-outcome ledger. The static oracle resolves exact product-token closure; the prerequisite judge reviews first-action sufficiency. No second implementation is required at Standard tier.

## Bounded gaps that cannot be solved in the skeleton

- Actual first-hour completion, seat-time, spend, scorer time, accessibility, inter-rater agreement, hidden-case custody, transfer, and 200-learner capacity require adapters and pilots.
- Legal applicability requires local policy/legal owners.
- A dynamic protected checker can be specified and bounded in core; its implementation cannot be guaranteed by the skeleton.
- Stochastic repetition requirements can be predeclared; sufficient sample size depends on the task and observed variance and must remain bounded rather than universal.
