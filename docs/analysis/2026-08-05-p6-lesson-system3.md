# System 3 Analysis: P6 lesson architecture

Date: 2026-08-05

## Context

- P6 currently asks learners to summarize four static files, then spend most of the block on approval modes, a control register, interruption, hostile input, scheduling, and Pi tool-schema evidence.
- P2 already teaches the difference between advice and a rule that always runs. P5 already teaches hostile-input containment. PG already runs unattended workers. P7 follows P6 and teaches the difference between an adaptive loop and a fixed line.
- The present Goose and Pi procedures contain release-blocking command and evidence defects, but repairing those defects would preserve the same curriculum shape.
- The learner experience must work on Windows with local synthetic evidence, a funded xAI key, and the current stable Goose CLI.
- The requested experience is the visible leverage of agentic work. Reliability mechanics may support the run backstage; they are not the lesson.

Unknowns remain: the exact learner-role mix, provider latency during the cohort, managed-device policy on autonomous mode, and the selected model's consistency on the final fixture.

## Problem Frame

Three useful statements of the problem:

1. **Curriculum:** P6 needs one capability that PG, P5, and P7 do not already teach.
2. **Experience:** one short human direction must cause enough coordinated, adaptive work that the learner feels the leverage before studying the mechanism.
3. **Delivery:** the run needs an observable before/after state and a deterministic finish without turning setup and assurance into learner work.

Assumptions under test:

1. Scheduling is not required to experience autonomous goal pursuit.
2. A long run does not feel powerful unless progress and state change are visible.
3. Multi-file summarization can look like batch processing and is too weak as the central demonstration.
4. Learners can own a mission by changing one consequential policy; they do not need to edit recipe YAML.
5. A local synthetic workload is more reliable than a live external integration and can still feel operationally real.
6. A machine checker makes the agent's observe-and-revise loop legible.
7. A useful watch board, action queue, and morning brief create more perceived leverage than a transcript or tool-call count.
8. A second wave of information is the clearest way to distinguish a living agentic product from a one-shot summary.
9. Goose remains a suitable runtime when the learner keeps the full installed profile and the launcher adds the native Developer toolkit needed for the mission.
10. The learner should make one consequential judgment so the exercise demonstrates delegation, not a passive demo.

## Perspectives

### Curriculum skeptic

The existing lesson assesses Goose and Pi operation more strongly than agentic leverage. Retaining the title and scenario is useful, but the objective, artifacts, and outcome rubric need replacement. This challenges the assumption that fixing command drift fixes the lesson.

### Operations practitioner

The useful pattern is a changing queue becoming a maintained decision product. The agent should correlate updates, revise prior conclusions, and park one question for a person. This challenges the assumption that a calendar schedule or a forced interrupt demonstrates ownership of operating work.

### Learner advocate

The first twenty minutes need a shareable reveal: a visibly red package becomes a usable board and brief through a loop the learner did not direct step by step. This challenges the assumption that more setup creates more understanding.

### Workshop engineer

Live integrations, persistent schedules, two CLIs, and manual evidence collection create fragile room dynamics. A foreground PowerShell wrapper, one fixed current workspace that can be rebuilt, a local fixture, and a deterministic verifier give the instructor a recoverable path. This challenges the assumption that realism comes from external dependencies.

### Futurist

Session-file formats and CLI details will keep moving. Goal, state, action, feedback, revision, and completion survive vendor churn. This challenges the assumption that product-surface coverage is transferable learning.

### Conflicts and agreements

All perspectives reject the current static summarizer and the safety-mechanics center. The main tension is between a two-wave adaptive watch and an executable recovery mission. Combining them preserves the operational scenario while adding a visible feedback loop: clear a red overnight watch, then absorb new traffic and update the same product.

## Creative Reframes

1. **Restaurant expeditor analogy:** new tickets keep arriving, related items must stay together, and only exceptions should interrupt the person. The product is the live board, not a report written after service.
2. **Inversion — power first, mechanism second:** launch a prepared mission before teaching recipe fields. Inspect what the agent coordinated only after the useful product exists.
3. **Pre-mortem:** the lesson fails if the run resembles one large prompt, if the learner waits without a useful product, if the output cannot be checked, or if setup consumes the block. A checked command center, a maintained machine state, a clean current workspace, and a consequential second-wave delta address those failure modes.

## Synthesis and Recommendation

Retain **P6 — The Watch Officer** and replace its exercise with **Clear the Overnight Watch**.

The durable capability is:

> Give an agent ownership of a changing operational objective, let it choose and revise the work needed to reach a checked finish, then use one human judgment to change the product coherently.

The learner arc:

1. Run one supported PowerShell command that hands four mixed overnight feeds to full Goose.
2. Open one useful command center and judge Goose's provisional allocation of the only mobile power unit.
3. Learn that the world changed: one earlier emergency recovered while an ambulance route and a regional relay now compete for the same unit.
4. State one consequential operating intent in plain language without prescribing the implementation.
5. Run the update and let Goose revise the same command center and machine state to a checked finish.
6. Inspect the visible before/after account: NEW, CHANGED, CANCELLED, and UNCHANGED.
7. Explain why the changing watch needed an adaptive loop rather than P7's fixed line.
8. Map the pattern onto one recurring workload from the learner's desk.

Remove from required P6 work: Pi, scheduler setup, approval-mode instruction, control taxonomy, hostile-input handling, YAML editing, and forced stop/restart proof.

Keep backstage: a clean current workspace, authoritative prepared evidence, a deterministic outcome checker, a prepare-only CI path, and a clean retry lane. Use capability checks instead of numeric Node or Goose version gates. Do not narrow the learner's Goose profile, cap turns, or require transcripts, receipts, snapshots, or extra artifacts.

## Blind Spots and Uncertainties

- A funded Windows pilot may reveal quoting, execution-policy, provider, or model-format issues.
- The fixture needs enough operational richness to avoid feeling like document cleanup.
- The checker must enforce completeness without rewarding token stuffing.
- Provider latency may require adjusting the event set, but the exercise should not impose an artificial turn ceiling.
- Learners already fluent in agents may need an optional third wave or their own mission card for depth.
