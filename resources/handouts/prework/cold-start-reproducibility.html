Verify setup from a fresh start

Use this optional check when setup worked only after terminal changes, app restarts, or instructor help. It answers one practical question: after a safe Windows restart, can the workstation regenerate the three course smoke files from a new shell and newly opened apps?

Complete the course harness and tool verification first. Then allow 15–20 minutes plus restart time. The result is three fresh smoke files.

Finish line The old smoke files are out of the designated folder, the laptop crosses a fresh-start boundary, and Codex, OpenCode, and goose each create their expected file again. If any tool needs an old terminal, an old file, or a remembered repair, return to that tool’s install check.

Know what a restart actually tests

A warm setup can succeed for the wrong operational reason. An open terminal may carry a session-only key or PATH edit. An app may still be open in the correct folder. A background process may still be running. Yesterday’s output may look like today’s success. A fresh start removes those temporary helpers while preserving the installed software and saved configuration you intend to use.

Separate temporary state from durable state

StateWhat can mislead youWhat the fresh-start check requires
Shell processSession-only variables or a temporary PATH editA newly opened PowerShell window resolves the tools and sees secret-safe key presence
Open appA remembered project folder or cached authentication screenOpen each app again and navigate using the written course path
Old outputA file from the warm setup looks like a current passMove old smoke files aside and watch each expected file appear again
External serviceProvider outage, quota, ACL, or organization network policyIdentify the external boundary; do not reinstall a healthy local tool

The not-obvious Windows detail is process inheritance: a PowerShell process receives an environment when it starts, and child processes inherit that environment. A setting changed only in one terminal can make that terminal work while every future terminal fails. Microsoft documents the scopes and inheritance behavior in about_Environment_Variables.

A restart does not make the laptop “fully clean.” It intentionally preserves installed tools, saved user or machine settings, credentials, and external account state. The check is bounded: it shows that the course workflow survives loss of open-process state. It does not show that another account, laptop, network, or provider will behave the same way.

Example: the tool worked only in the setup terminal

Leena completes the OpenCode smoke check after setting a key and adding the install folder inside the current PowerShell process. The expected file appears. After a restart, a fresh terminal cannot find the command and cannot see a saved key. The warm result was real, but it depended on process-only state.

The correct diagnosis is not “OpenCode is broken.” The executable and credential configuration were never made available to future processes. Leena returns to the current install instructions, uses the approved persistent setup path, opens another fresh terminal, and repeats the smoke check. The command now resolves and a new smoke file appears.

This distinction saves time: reinstalling the tool without checking process scope can repeat the same failure, while inspecting a fresh process immediately identifies whether the durable setup is missing.

Run the fresh-start check

  1. Finish the normal verification first. Confirm that all three current smoke files exist and contain the expected text.
  2. Move old smoke files aside. Put the three from-*.txt files in a temporary dated folder beside the smoke folder. Leave the designated smoke folder empty.
  3. Restart safely. Save unrelated work, restart Windows, and open a new PowerShell window. If a restart is unsafe on a managed machine, close every relevant terminal and app and treat the result as a weaker process-fresh check.
  4. Check durable setup. Run the current secret-safe key-presence and command/version checks. Never print or paste a secret value.
  5. Regenerate the files. Follow the current three tool checks. Inspect the folder after each tool and confirm that its file appears with the expected contents.
  6. Fix the actual boundary. If a key or command is missing only in the fresh process, return to that setup section. If the tool starts but provider access fails, check network, account, quota, and ACL status before changing the installation. After the fix, open a fresh process and rerun only the affected check.

Stop condition Do not clear credential stores, change organization policy, expose a key, uninstall unrelated software, or use work data. Bring the exact symptom and the last successful boundary to the install clinic.

Use the result

If the three files regenerate, the workstation is ready for the course path. If one tool fails, use The Install Fault Tree to identify the first boundary that did not work, then return to the matching install step. You do not need a separate setup report.
