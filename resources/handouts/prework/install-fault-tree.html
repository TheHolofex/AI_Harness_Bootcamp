Find the first boundary that failed

Use this guide when an install or smoke check fails and the next move is unclear. It separates six boundaries—shell, path, runtime, identity and access, local policy, and tool behavior—so you can fix the layer that actually failed instead of reinstalling at random.

Finish line Identify the first boundary that did not behave as expected, take one low-risk action that addresses that boundary, and rerun the affected course check. If the next action needs administrator authority or would expose a secret, stop and bring the exact error to the install clinic.

Read the failure from left to right

Error messages often name a component near the symptom, not the underlying cause. Start with the last boundary you can directly observe. A credential cannot explain a command that never started; a reinstall cannot fix authorization that was denied by a remote service.

BoundaryQuestionUseful observation
ShellDid the intended shell receive and parse the command?Shell identity, exact command, parsing error
PathDid the name resolve to the intended executable?Get-Command result and resolved location
RuntimeDid that executable load and begin?Version output, startup error, process behavior
Identity & accessWas identity established, and was the requested action allowed?Authentication versus authorization response
Local policyDid Windows or organization policy block the action?Policy dialog, execution restriction, managed-device notice
Tool behaviorDid the running, permitted tool perform the task and leave the expected artifact?Tool output, expected file, file contents

Authentication establishes who or what is presenting a credential. Authorization decides what that identity may do. Keeping them separate prevents a common waste: rotating a valid key when the account is authenticated but lacks permission or quota.

Choose a probe that changes the decision

  1. Capture the exact symptom. Keep the error text, command, time, working folder, and expected result before changing anything.
  2. Locate the last successful boundary. If the name never resolves, later boundaries are not reached. If the service recognizes the identity and denies the action, installation and authentication already worked.
  3. Compare one meaningful condition. A fresh terminal versus an old terminal, or the exact installed path versus the short command name, usually separates more causes than another reinstall.
  4. Make the smallest reversible correction. Address the first failed boundary, then rerun the current course check from a fresh process.

A probe is valuable only if its possible results lead to different next actions. If every result would make you reinstall, the probe has not narrowed the problem.

Example: the install succeeded but the command is missing

Mara installs a command-line tool in a terminal that was already open. The installer reports success and the executable exists at the recorded location, but entering the command returns “name not recognized.” No tool process begins and no smoke file is created.

The first failed boundary is path resolution, not credentials or provider access. Mara compares the old terminal with a fresh PowerShell window while keeping the user, machine, and command fixed. The fresh window resolves the installed executable; the old terminal does not. The old process inherited its PATH before installation.

She closes the stale terminal, uses the fresh one, and runs the current smoke check. Only after the program starts would runtime, authentication, authorization, policy, and final tool behavior become live questions. This boundary order prevents unrelated fixes from erasing the useful symptom.

Diagnose the failure you actually have

  1. State the top event. Write one sentence with the command or action, expected behavior, actual behavior, and observation point.
  2. Mark the first failed boundary. Work through shell → path → runtime → identity/access → local policy → tool behavior. Stop at the first boundary that lacks supporting evidence.
  3. Run one low-risk comparison. Prefer inspection or a fresh-process comparison over changing configuration. Keep secret values out of screenshots and notes.
  4. Apply the matching correction. Use the current install section for that boundary. Do not add unrelated upgrades or cleanup.
  5. Rerun the affected smoke check. Success requires the intended tool to start and create the expected file with the expected contents.

Resolve it or bring a precise blocker

If the correction works, continue with the normal setup path. If it does not, avoid accumulating speculative changes. Return to the install recovery checks or bring the blocker to the install clinic with the exact symptom and last successful boundary.
