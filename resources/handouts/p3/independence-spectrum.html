Use it before agreement becomes corroboration

Two outputs can look like two witnesses while sharing the same blind spot. A different provider, model label, or reviewer name tells you that one component changed. It does not tell you whether the paths were exposed to different evidence, transformations, evaluation rules, or pressures.

Plan for 45–60 minutes. You will leave with an independence ledger: a record of the shared state between two paths, the common failure each connection could produce, the isolation move that breaks that connection, and the dependence that remains afterward.

Start after P3 · Twin-engine intel desk, where you set the frozen brief, clean-run conditions, run identity, and comparator. The move here happens before you treat any agreement as independent support: map how the two paths could still become wrong together.

Independence is a profile, not a badge. Name the failure you are trying to resist, then show which causal paths are actually separated. Do not turn the profile into a percentage or a claim of statistical independence.

Model the failure path, not the brand count

A common cause is one upstream condition that can make more than one path fail. A common-mode failure is the similar wrong behavior those paths display. One omitted record in a shared summary is a common cause; two reviewers recommending the wrong vendor because neither saw that record is the common mode. The terms matter because changing the outward reviewer does not remove the upstream cause.

Operational independence means that, for a named failure, the paths differ at the points capable of producing it. It is intentionally narrower than statistical independence. Statistical independence is a claim about the joint probabilities of defined events under a defined input distribution. A ledger with many separated rows does not supply that model or those observations.

The old experiment behind the modern warning

N-version programming attempted to tolerate software design faults by running separately developed implementations of the same specification and applying a decision function to their outputs. Its architects treated diversity in algorithms, languages, tools, teams, and execution sites as potentially useful, while also recognizing that the specification and the decision environment remained shared dependencies (Avizienis, 1985).

Knight and Leveson then tested 27 separately developed programs on one million inputs. Coincident failures occurred substantially more often than the tested independence model predicted. Their conclusion was not that diversity is useless. It was that independent development does not justify assuming independent failures, and reliability analysis must account for dependent error (Knight and Leveson, 1986). The uncomfortable part is that some shared failures appeared to arise from difficult problem semantics and common human misconceptions, not merely from a sloppy specification.

That lesson transfers cleanly to AI work. A recent study across more than 350 language models found substantial error correlation; shared providers and architectures explained some correlation, but distinct providers and architectures did not remove it (Kim et al., 2025). “Different model” is useful evidence about one dimension. It is not a verdict about the whole path.

NASA fault-tolerance guidance makes the systems version of this point: a common cause can cross several nominal containment regions, and even the mechanism that manages redundancy can become a shared point of failure (NASA, 2008). NIST likewise treats diversity as multidimensional—structure, behavior, interfaces, data and control flow, and technology—and warns that diversity adds cost and complexity that still need verification (NIST SP 800-160 Vol. 1 Rev. 1).

One dependence cannot be removed without changing the job: the problem itself. Two paths can encounter the same difficult boundary, ambiguous real-world category, or common misconception even when every controllable layer differs. Record problem semantics under residual dependence. A new provider cannot isolate it; only clearer evidence, a better-specified decision, or accountable human judgment can reduce that risk.

The frozen-control paradox

Shared state is not automatically a defect. When you want to attribute differences to engines, a frozen brief and identical corpus are deliberate controls. Changing the brief, evidence, and model at once buys diversity but destroys the attribution. When you want independent corroboration of a claim, the shared corpus may be the exact dependence you need to reduce.

Write the purpose at the top of the ledger: controlled engine comparison or diversified corroboration. The first holds more constant. The second separates more evidence-producing stages. Both can be honest. Confusing them produces a comparison that answers neither question.

Use this bounded claim shape:

For failure class [H], paths A and B differ in [dimensions].
They still share [residual dependencies].
Their agreement therefore corroborates against [bounded failure classes],
but does not address [remaining common causes].

Break it on purpose: perform a brand swap

To inject the failure, return Path B to the shared summary, shared index, and shared evaluator. Change only the provider and prompt wording, then run the non-acting review. The diagram still has two engine boxes, and the outputs may sound different. The observable symptom is more damning: both repeat the same wrong incident count, and the evaluator cannot detect it because its reference surface carries the same omission.

Diagnose against the pre-run ledger. The source-data, retrieval, and evaluator rows already name the paths capable of producing this joint failure; the observed count tells you those threats were not theoretical. A shared node that cannot cause this failure is a residual to record, not a reason to rebuild everything. If no ledger existed before dispatch, do not invent a clean pre-run story afterward—record the gap and run a separate silent-agreement audit.

Recover by splitting the path before that node. If raw evidence cannot be supplied safely, add a human check at the earliest approved boundary and narrow the claim. Do not add a third model to the same evidence pipe; that increases the appearance of support without changing the common cause.

Also guard against over-isolation. If you change the decision question for Path B, the two outputs no longer answer the same demand. Preserve the shared state needed for comparability, separate the state capable of causing the named failure, and record both choices.

  1. Predict. Which dimensions are separated with evidence, shared by design, shared uncontrolled, or unknown? Decide before opening the reveal.
  2. Trace. Fill at least five ledger rows. Each plausible common failure must name a causal path, not merely say “bias.”
  3. Prioritize. Circle the shared node most capable of producing the named failure. Do not count rows; use causal relevance and consequence.
  4. Spend the isolation budget. Choose one move that breaks that path while keeping the fixed venue criteria comparable.
  5. Bound the claim. Complete the four-line corroboration statement and name what a human must still decide.
Reveal the threat map after you commit

The engine and context dimensions are partly separated. The criteria sheet is shared by design. Source preparation, retrieval, evaluator, and reporting pressure are shared uncontrolled for the named failure. The strongest 20-minute move is not another engine: give the facilities coordinator the raw proposal and ask for an evidence-only check of the accessible-route criterion, then let Path B use that raw-field result without the shared OCR index. The spreadsheet formula remains a residual for cost, and the criteria, source authenticity, and coordinator judgment remain shared dependencies. Agreement may now corroborate against the OCR/index omission only; it still does not prove overall venue suitability.

Stop conditions: stop if the raw proposal cannot be handled on an approved surface, if the criteria or decision authority are disputed, or if the available reviewer is not permitted to inspect the evidence. Return the venue decision to a human if a critical source remains unavailable, the residual dependence dominates the recommendation, or any contact, commitment, or spending action would follow.

Transfer one claim without rebuilding your desk

Choose one consequential claim you expect two reviewers or engines to examine this week. In 15 minutes, name one failure that could fool both, sketch each source-to-verdict path, and fill the three ledger rows most capable of producing that failure. Select one isolation move you can actually prove happened. If no feasible move breaks the dominant coupling, do not decorate the result as corroboration; narrow the claim and return it to the decision owner.

Keep run identity and reconstructable evidence with the work; use Reproducible Runs for that record. If you need to know whether behavior holds across repeated generative trials, use One Run Is a Probe, Not Proof. Neither artifact substitutes for the dependency map here.

After the paths run, return to the P3 comparator and human adjudication process. The ledger tells you what agreement could mean; it does not decide whether the agreed claim is true.

Human return: stop before action when a critical source is unavailable, protected data would cross an unapproved boundary, evaluator separation is impossible under material sponsor pressure, or the consequence of shared error exceeds what the remaining checks can bear. A human owner decides whether to gather new evidence, accept the bounded risk, or halt.
