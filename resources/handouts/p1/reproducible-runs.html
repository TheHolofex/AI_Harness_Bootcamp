Use it when someone must reconstruct the run, not just read the answer

A brief has reached a decision meeting. Two days later, a source changed, the machine ran again, and somebody asks which evidence and settings produced the version that was approved. The file called final-brief.md cannot answer. It may have moved, been replaced, or been regenerated from different material under the same name.

Plan for 45–60 minutes. You will bind one evidence-bearing execution into a run manifest—a bounded record of its identity, inputs, configuration, execution, outputs, and operator verdict—and leave with a replay checklist another operator can follow without reconstructing the run from chat memory.

Start after the regenerable path in P1 · Going deeper exists. P1 proves that you can run the machine again. This method answers a narrower question: what exactly was run this time, and what evidence would let us reconstruct or replay it?

Keep the neighboring claims separate. Pre-work’s cold proof asks whether the workstation survives a fresh start. P1’s metamorphic field guide compares behavior across deliberately transformed inputs. P3 asks how independent two runs or engines really are. Here you are binding one particular run so it can be identified, inspected, and replayed. A strong manifest does not prove cold readiness, behavioral correctness, or independence.

Treat the run as an evidence bundle

An output file is one entity. The run is the activity that used source and configuration entities to generate it, under the responsibility of an operator and a machine. That input–activity–output shape comes from the W3C’s domain-neutral provenance model, which separates entities, activities, and responsible agents so later readers can assess reliability rather than infer lineage from a filename (W3C PROV-DM).

Your bundle therefore needs five parts: an identity for the execution, the exact input snapshot, the machine and configuration that shaped the run, an execution record, and the raw output plus the human verdict. Leave one part out and a later operator must guess. A guess can still produce a fluent brief, which is why missing provenance is hard to notice from the answer alone.

Give identity, location, and content different jobs

A stable run ID is an immutable reference minted for one execution, such as OPS-RUN-20260731-0042. Never reuse it, even when a run crashes or a replay is intended to reproduce the first one. Give the replay its own ID and record replay_of. Also name the ID namespace and its allocator—the rule or registry that issues the next value. A date-plus-counter is unique only where one controlled register prevents duplicates; independent writers need a standard UUID or an equivalent allocation scheme (RFC 9562). The ID preserves reference after paths move. It does not authenticate the run or prove its content.

A filename or path is a locator. current/brief.md tells you where bytes are expected now; it does not prove those are yesterday’s bytes. A source ID names the logical item in your work system. A content hash identifies the bytes you actually inspected. These fields can point to the same artifact, but they are not substitutes for one another.

A cryptographic hash runs a named algorithm over bytes and returns a fixed-length digest. NIST’s Secure Hash Standard describes digests as a way to detect whether messages changed after the digest was generated (NIST FIPS 180-4). The IETF’s BagIt format applies that mechanism in manifests: each payload path is paired with a checksum, and validation recomputes the checksum against the file (RFC 8493).

That is a byte-level claim, not a truth claim. A matching digest does not establish that a note is accurate, authoritative, safe, or supposed to be included. It only supports the statement that the observed bytes match the bytes named by a trusted reference, within the limits of the algorithm and procedure. If somebody can replace both the file and its manifest, an unsigned hash does not expose that attack. Keep the reference in a controlled record or add the stronger protection your organization requires.

The reverse limitation matters too: semantically identical text can hash differently because its encoding, line endings, spacing, or metadata bytes changed. Record the algorithm and hash the files as they actually entered the run. Do not call a hash mismatch “changed meaning” until you inspect the difference. Standards for hash-based names make the same separation: the digest can name content, while the mechanism for locating and trusting that content remains a separate concern (RFC 6920).

Write a bounded manifest, not a completeness claim

A useful manifest records the factors you could observe and control, then names what was not exposed. Supply-chain provenance systems use a similar split among a subject output, a build definition with parameters and resolved dependencies, and details of the particular execution. The exact schema is for software builds, but the design lesson transfers: record both the reusable process definition and this run’s resolved facts (SLSA v1.2 Build Provenance).

Keep expected inputs separate from the resolved snapshot. A manifest can perfectly hash the wrong file. It can also list a file that the machine never read. Hashes protect identity of recorded bytes; P1’s source probes and external checks establish whether the machine used the intended boundary. If the runtime does not expose a model revision, hidden context, or service state, write not exposed. Fabricated precision is worse than a visible gap.

The National Academies defines computational reproducibility as obtaining consistent computational results using the same input data, steps, methods, code, and conditions of analysis (Reproducibility and Replicability in Science). Generative machines add an honest limit: recorded inputs and configuration can still yield different prose. A peer-reviewed study of five hosted LLMs across eight tasks found output variation across repeated runs even under settings intended to be deterministic (Atıl et al., 2025). Classify a replay in this order:

  1. If any required recorded bundle field differs or is unavailable, record not established.
  2. If the bundle matches and the output digest matches, record byte stood.
  3. If the bundle matches, the output digest differs, and the fixed decision surface plus acceptance checks match, record behavior stood.
  4. If the bundle matches and a comparable decision field or check differs, record controlled divergence.
  5. If the run or output cannot be compared, record inconclusive and name the missing comparison.

original is a record type, not a replay result. The result labels above apply only after an operator attempts a replay.

Never leave the word “reproducible” unqualified. Name the comparison surface, the matched conditions, and whether byte stood or behavior stood. “Consistent result” is not a license to slide between identical files and equivalent operational decisions.

None of those labels proves the product true. The operator still checks evidence and owns the verdict.

Diagnostic example: the path matched but the contract did not

A museum registrar prepares an outbound-loan dispatch certificate for loan ML-042. The fixed certificate fields are Loan ID, Disposition, Release holds, Responsible functions, Dispatch review, and Evidence gaps. The original run, ML-RUN-014, reports HOLD because a conservation courier is unassigned. Its manifest records four source snapshots and machine/release-contract.md.

One week later, Mina replays the run for an audit. She copies the named files, uses the same saved run path, and receives RELEASE. The structure is complete and every source filename matches. Her first diagnosis is: “The model changed, so this machine is not reproducible.” That is a plausible overclaim. She has not yet shown that she reconstructed the run.

The bounded verdict is: “The first attempt was not established because it did not reconstruct the recorded configuration. Under the observable input and configuration bundle from ML-RUN-014, the second replay achieved behavior stood, not byte stood; unexposed execution state remains unknown.”

Notice what the recovery did not say. Matching the original contract hash did not prove the contract was good. Matching the decision surface did not prove the certificate was factually correct. The manifest localized one cause of divergence and made the remaining claim smaller.

Use one byte-hashing contract

For every run, calculate SHA-256 over the stored file bytes and retain all 64 hexadecimal characters. Use the same byte-preserving method for original and replay; record that method and each exact stored path. Hash stored inputs, configuration, and procedure before execution, then hash the raw output immediately after. Do not open, resave, re-encode, or normalize a file before hashing it. Recompute and compare digests exactly. A mismatch means the bytes differ: inspect or stop. It does not by itself mean the meaning changed.

  1. Freeze the procedure. Place only the four source files in current/ and the original contract in machine/contract.md. Save the exact accepted instruction or command text that invokes your machine as replay-practice/procedure.md. If you cannot materialize the procedure, stop; replay will be not established.
  2. Mint the original ID. Use RP-[date]-001 only inside a controlled practice namespace, or use your team’s normal immutable scheme. Record its namespace, allocator, purpose, operator, start time, saved run path, working folder, and exposed execution identity.
  3. Create the original bundle. Before execution, copy the exact bytes into runs/RP-[date]-001/inputs/, runs/RP-[date]-001/config/contract.md, and runs/RP-[date]-001/procedure/procedure.md. Hash those stored copies. Confirm the working copies match them, point the manifest to the stored paths, and record IDs, roles, full digests, method, and any not exposed fields.
  4. Run and seal the result. Execute once from the verified working copies. Save the untouched raw output inside the same run bundle, hash it immediately, reduce it to the five storage-record fields, and close the manifest. Do not edit or overwrite the stored evidence.
  5. Declare the replay comparison. Record the decision-bearing fields that must remain stable: storage disposition, custody state, and transfer window. Treat exact wording and the output hash as separate comparison surfaces.
  6. Create a verified replay. Mint a second ID linked by replay_of. Copy the original bundle’s stored inputs, configuration, and procedure into the replay bundle and restore the working copies from those stored bytes. Verify every digest against the original before execution, run once, and store the untouched raw output and manifest.
  7. Issue the bounded verdict. Compare input and configuration digests first, then the decision surface, acceptance checks, and output digest. Record behavior stood, byte stood, diverged, or not established with the exact first mismatch and any unexposed execution state.

Expected decision surface

The source record is: batch ID SB-74; packet count 18; storage disposition QUARANTINE; custody state: witness unassigned; transfer window: Wednesday 14:30. When the stored inputs, contract, and procedure all match, those five fields and their acceptance checks should hold. If only prose or the output digest differs, record behavior stood; if the output digest also matches, record byte stood. Any required input or configuration mismatch makes the replay not established until the recorded bundle is reconstructed.

Stop and return control if the original bytes cannot be recovered, an influential setting is unknown and outcome-critical, hashing or storing the record would violate data policy, or replay could trigger a live action. Preserve the manifest with not established; do not repair the historical record by guessing.

Replay checklist

  1. Locate the original by stable run ID, not by a folder called latest.
  2. Read the original verdict, residual unknowns, and stop conditions before executing.
  3. Restore work on copies. Recompute every source, procedure, and configuration digest.
  4. If a recorded influential field differs or is unavailable, stop and label the replay not established.
  5. Mint a new run ID and link replay_of; never reuse the original ID.
  6. Run the recorded path once. Save and hash the raw output before editing.
  7. Compare exact output digest and decision surface as separate checks.
  8. Apply the ordered rule: not established, byte stood, behavior stood, controlled divergence, or inconclusive. Record the first discriminating difference.
  9. Run the product’s external evidence checks. The replay never inherits the original human verdict automatically.

Apply four replay rules consistently

  • The same filename with a different SHA-256 digest is a different recorded input. Inspect the diff, correct the reconstruction, or record that the original bytes are unavailable.
  • Matching inputs and configuration with different prose can still achieve behavior stood when every decision field and check holds. Record the output-digest mismatch separately.
  • A matching output digest establishes byte identity, not factual correctness. Source support, authority, inclusion, safety, and the operator verdict still need their own checks.
  • Every attempt keeps its own run ID. After a fix, preserve the failed activity, mint a new ID, and link the relationship.

Bind one low-stakes desk run

Choose one recurring product that already has a saved run path: a queue watch, project rollup, readiness note, or weekly risk brief. Work on copies and keep the run non-acting. In one 30-minute pass, mint a run ID, inventory and hash the procedure, configuration and inputs, run once, save the raw output, and record the decision surface plus your verdict.

Then hand only the manifest and authorized snapshots to a colleague—or to yourself in a fresh work period—and attempt reconstruction. The test is not “can they get a similar paragraph?” It is “can they account for every material match, mismatch, and unknown before they judge the result?”

Do not treat a digest as declassified data, and do not copy protected material into an unapproved store. Stop when an input cannot be frozen lawfully, a hidden dependency controls a high-stakes decision, or the replay could issue a notification, transaction, or production change. Return the gap to the product owner. A bounded not established record is stronger evidence than a confident replay built from guessed state.

Sources worth keeping

  • W3C — PROV-DM: The PROV Data Model. The entity, activity, agent, usage, generation, and derivation distinctions behind the run bundle.
  • National Academies — Reproducibility and Replicability in Science: Highlights. A precise definition of computational reproducibility and the reporting needed to support it.
  • NIST FIPS 180-4 — Secure Hash Standard. The standard basis for using message digests to detect changed bytes.
  • IETF RFC 8493 — The BagIt File Packaging Format. A practical standard for inventorying files and validating them with manifests.
  • IETF RFC 6920 — Naming Things with Hashes. The relationship among content digests, identifiers, and location.
  • IETF RFC 9562 — Universally Unique IDentifiers. One established option for minting execution identifiers without deriving identity from filenames.
  • SLSA v1.2 — Build Provenance. A mature input, dependency, execution-detail, and subject-output pattern that informs bounded run manifests.
  • Atıl et al. — “Non-Determinism of ‘Deterministic’ LLM System Settings in Hosted Environments”. Evidence that the same inputs and ostensibly deterministic settings do not by themselves guarantee identical hosted-model outputs.
