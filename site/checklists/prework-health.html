How to run this gate

  1. Not a second machine, not a machine you tested on last week. If you'll carry two, run this on the one that will be open during class.

  2. Close everything and open one new PowerShell window. A window that has been open since you were installing may be carrying variables that won't exist on Monday, which would let a broken setup pass.

    Confirm it is PowerShell and not Command Prompt or Git Bash — every command below assumes it:

    $PSVersionTable.PSVersion

    A version number means you're in the right window. An error means you're somewhere else.

  3. Anything that fails here gets written down: the step, the exact error, what you tried. That log is part of what you show Monday.

A · Foundations

  1. [Environment]::Is64BitOperatingSystem
$env:PROCESSOR_ARCHITECTURE

    You want True and AMD64. ARM64 is a blocker you must raise with staff rather than work around.

  2. git --version
node -v
npm -v
python --version

    Four version numbers, no errors. Node must read 22.22 or higher and below 25 — anything outside that range breaks n8n on Thursday and Pi today.

  3. Test-Path "C:\Program Files\Git\bin\bash.exe"

    If False, check the per-user location instead and record whichever is real:

    Test-Path "$env:LOCALAPPDATA\Programs\Git\bin\bash.exe"

    Pi needs this. Write the working path in your log.

  4. Get-ExecutionPolicy -List

    CurrentUser should read RemoteSigned. Just as important: MachinePolicy and UserPolicy should both read Undefined. If either is set, IT is overriding you and some installers will keep failing however many times you retry.

  5. (Get-Command python).Source

    A path containing \WindowsApps\ means the Microsoft Store placeholder is intercepting the command. Fix it before Monday — see step 22 of the install checklist.

B · Your three keys

  1. 'OPENAI_API_KEY','XAI_API_KEY','ANTHROPIC_API_KEY' | ForEach-Object {
  '{0}: user={1} session={2}' -f $_,
    [Environment]::GetEnvironmentVariable($_,'User').Length,
    (Get-Item "env:$_" -EA SilentlyContinue).Value.Length
}

    Three lines, two matching non-zero numbers each. This is the check that matters most in this section, because you're running it in a fresh window — which is what Monday will be.

    Only lengths print, never the keys, so this is safe to run while someone watches.

  2. The four write proofs below are the real test of this. If a tool that worked during install now fails with a 429 or a message about quota or spend limits, the key has hit its cap rather than broken.

    Message staff with which key and what you were running. This is a two-minute fix on their side and not something to reinstall over.

C · Four required agents — files on disk

  1. This is the heart of the gate, so don't accept files you made days ago on a machine state you no longer have. Delete them and make each tool prove itself again:

    cd "$env:USERPROFILE\Documents\HarnessBootcamp\prework-smoke"
Remove-Item from-*.txt -ErrorAction SilentlyContinue

    Then re-run the four write commands from the install checklist, steps 36, 43, 47, and 55.

    If that feels like repetition, it is — and it's the same discipline the whole week runs on. A result you can regenerate on demand is worth more than one you happen to still have lying around.

  2. This one you ask for in the app rather than typing a command. Open the smoke folder as a project, then request the file in plain language:

    Create a file named from-codex.txt in this folder containing exactly the text: codex works

    Then confirm it landed:

    Get-Content .\from-codex.txt

    Check two things in the app while you're there. The profile menu must report API-key authentication, not a ChatGPT account — if it names an account, the course path isn't set up, so redo install step 31. And the permissions control beneath the message box should read Ask for approval, which is what keeps the sandbox on.

  3. opencode --version
$env:OPENCODE_DISABLE_CLAUDE_CODE
Get-Content .\from-opencode.txt

    Record the version in your log — Monday asks for it by name, because Tuesday's twin-engine comparison only means something if you know which build produced it.

    The middle line should return 1. That is what stops OpenCode reading ~/.claude/CLAUDE.md and .claude/skills and running Tuesday's comparison on the other engine's notes. A blank line means re-set it from install step 43.

    If OpenCode claims success but no file appears, that's the known Windows defect. Log the version and exact wording and tell staff; don't keep retrying.

  4. Get-Content .\from-pi.txt
Get-Content .\bash-check.txt

    Both files matter. The first proves Pi authenticated and wrote; the second proves it can reach Git Bash. Pi only looks for a shell at the moment it needs one, so without this second check a missing shell stays hidden until it breaks an exercise.

    Also confirm you can state Pi's posture in your own words: no sandbox, no approval prompt, and no working-directory fence. Staying inside the smoke folder is a convention you keep, not a boundary Pi enforces. You'll build the bounds yourself later in the week — knowing what isn't there yet is the starting point.

  5. goose info -v
Get-Content .\from-goose.txt

    Check that goose info reports the provider and model you intended. It's easy to have goose working against a provider you didn't mean to use.

  6. Get-ChildItem "$env:USERPROFILE\Documents\HarnessBootcamp\prework-smoke\from-*.txt"

    Then open the folder in Explorer and look at it with your own eyes. That's the view you'll show Monday, and looking at it is the habit being trained.

    Missing any one of the four means not GREEN. Three out of four is a YELLOW at best, and only with a written account of the fourth.

  7. from-claude-optional.txt. Its absence does not affect your colour in any way — skip this line if you didn't install Claude Code.

D · Supporting tools

  1. Launch it and confirm your vault opens with no login screen.

    Get-ChildItem -Force "$env:USERPROFILE\Documents\HarnessBootcamp\vault"

    A .obsidian folder in that listing proves the vault is real rather than just a folder you made.

  2. Run n8n start in one window. In a second window:

    (Invoke-WebRequest http://localhost:5678/healthz -UseBasicParsing).StatusCode

    A 200 means it's genuinely serving. Then stop it with Ctrl+C in the first window and confirm the page stops answering.

    You should also be able to log into it with the owner email and password you set. If you've forgotten them, sort that out now rather than on Thursday.

  3. From the repository root run python -m http.server 8080 and open http://localhost:8080/site/. Stop it with Ctrl+C.

    Confirm you can also find mission_flesh/b0/reports/ in the repo — that's Monday's mission data, and knowing where it is saves you the first ten minutes.

E · Operator readiness

  1. Point at the folder and name the files: Direction Brief, Operator Log, pass bars, adversarial review, measurement spine, transfer.

    If you have to search for them Monday, they'll go unused. Put them where you'll actually be working.

  2. The Codex app on your OpenAI key and OpenCode on your xAI key. Claude Code, if you installed it, is an optional third opinion rather than a substitute for either.

    Say what each one loads before you type anything: the Codex app takes AGENTS.md, skills, and memories from wherever you launch it; OpenCode takes ~/.claude/CLAUDE.md and .claude/skills unless you've disabled that. Neither one tells you. Knowing this is what makes a comparison between them worth running.

  3. Tell staff immediately; they revoke and reissue. Then set the new key, and sign the Codex app in again through Sign in another way — it stored the old key rather than reading the variable each time, so it won't pick up the replacement on its own.

    Knowing this now is what makes reporting it fast later, and speed is the entire difference between a non-event and a problem.

  4. Something went wrong during install — a PATH that didn't refresh, a policy that blocked a script, a key pasted into the wrong variable. Write down what it was and what resolved it.

    If genuinely nothing broke, write that, and note the one step you'd least want to repeat from memory. Operators keep trails; a blank log is the one answer that doesn't hold up.

Gate result

  1. GREEN — foundations pass, all three keys verified in a fresh window, all four agent files regenerated and present, supporting tools launch. Ready for Monday.

    YELLOW — one thing is unresolved, you know exactly what it is, and you've written down where it stops. You'll start Monday with the room and get help alongside the work.

    RED — a required agent can't write a file, a key doesn't work, or you haven't been able to start. Say so before Monday rather than on it. Staff can usually clear a RED faster than you'd expect, but only once they know.

    YELLOW declared on Saturday is a better position than GREEN claimed on a step you skipped. The colour is information, not a grade.

  2. In your setup log: your name, the machine, the date and time you reached this colour, your OpenCode version, and your Codex app sandbox mode (elevated or unelevated).

    Those last two are the ones staff ask for most, because they're what differs between machines when something behaves oddly in class.

  3. Laptop and charger, the four proof files, your setup log, your colour, and anything still open that you want help with.

    Monday verifies this gate in the first twenty minutes and then moves straight to building something real. Arriving with a clear picture of your own machine is what makes that possible.
