Phase 1 · Prepare the machine

Before you begin

  1. We will complete installation and setup together during Monday morning’s clinic. Plan for two to four hours; a corporate-managed laptop can take longer because policy blocks appear one at a time.

    Bring the Windows 11 laptop you will use during the course. Keep this checklist open while the instructor walks the room.

  2. You need an OpenAI key starting sk-proj- and an xAI key starting xai-. Keep them separate: OpenAI goes only into Codex; xAI goes to every other cloud harness.

    If either is missing, tell the instructor and start with the machine steps anyway. The first four sections need no keys, so you can keep moving while the missing key is resolved.

  3. Foundations first: a terminal, the official installers for Git, Node, and Python, and a local copy of the course repository. You will clone the course as soon as Git works. After that you will connect your two keys and verify the course harnesses and tools.

    All of it is driven from one window — a PowerShell terminal. You'll open it in step 8 and stay there for the rest of this guide.

    The Codex app is your home for the week. OpenCode is the second harness you'll run the same brief through on Tuesday. Pi Agent Core runs ten supplied control-flow implementations on Thursday. goose then runs Thursday's prepared mission: it inspects a changing local watch, updates the working product, checks its own result, and revises until the mission is ready for you. Obsidian holds a knowledge base and n8n builds a fixed pipeline.

0 · Baseline machine

  1. Press Win+R, type winver, press Enter. Confirm the window says Windows 11.

    Then open PowerShell and check the architecture, because two tools here have no 32-bit build:

    [Environment]::Is64BitOperatingSystem

    You want True. Install any pending Windows updates now — doing it later tends to interrupt something mid-install.

  2. Snapdragon and other ARM Windows laptops — often sold as Copilot+ PCs — can't run this stack. OpenCode fails to start on Windows ARM64, and goose publishes no ARM build at all.

    $env:PROCESSOR_ARCHITECTURE

    AMD64 means you're fine. ARM64 means stop and tell the instructor before installing anything else. That's a machine question rather than something you can solve at the keyboard.

  3. Use the PowerShell window you already opened. This prints the free space directly, so you do not need to find This PC:

    $freeGB = [math]::Round((Get-PSDrive -Name C).Free / 1GB, 1)
"C: has $freeGB GB free"
if ($freeGB -lt 25) { Write-Warning 'Free at least 25 GB before continuing.' }

    You want 25 or more. If you need room, open Settings → System → Storage → Cleanup recommendations and review the suggested files before removing anything.

  4. Most steps install into your own user profile and need no administrator rights. Four prompt for elevation: Git, Node, the Microsoft Visual C++ runtime, and Codex's sandbox setup.

    If your laptop is corporate-managed and you can't approve an elevation prompt, tell the instructor. This may require an IT ticket that cannot be resolved from your seat during the clinic.

1 · Terminal and PowerShell

  1. Press Win, type Terminal, press Enter. Do not choose "Run as administrator" — the installers below ask for elevation individually when they genuinely need it, and running the whole session elevated can put things in the wrong place.

    Avoid the Start menu entry labelled Windows PowerShell (x86). That's a 32-bit host, and some installers refuse to run in it even on a 64-bit machine.

    This window is where every command in this guide goes. Windows ships three terminals that look similar, and commands are not interchangeable between them. Tell them apart by the prompt:

    WindowPrompt looks likeUse it for
    PowerShellPS C:\Users\you> — note the PSEverything in this guide
    Command PromptC:\Users\you> — no PSNothing here, unless a rescue step says so
    Git Bashyou@machine ~ $ — a $, and / in pathsOne Goose installer fallback

    Confirm you're in the right one:

    $PSVersionTable.PSVersion

    A version number means PowerShell. An error means you're somewhere else — close it and open Terminal again.

    Three errors later in this guide mean "wrong window" rather than "broken install", and they're worth recognising now:

    • 'irm' is not recognized — you're in Command Prompt, not PowerShell.
    • The token '&&' is not a valid statement separator — a Command Prompt or Git Bash style command pasted into PowerShell.
    • A parameter cannot be found that matches parameter name 'fsSL' — a Mac or Linux curl command pasted into PowerShell, where curl means something different. This is exactly what happens if you try OpenCode's website installer.
  2. $PSVersionTable.PSVersion

    Stock Windows 11 shows 5.1. That's expected, and it's enough for everything in this guide. You do not need to install a second PowerShell version for the course.

  3. Windows blocks PowerShell scripts by default. Several installers below — and npm itself — are scripts, so this has to change or they fail with an error that reads like a permissions problem but isn't one.

    Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser

    Answer Y if prompted. RemoteSigned means scripts you wrote run freely while downloaded ones must be signed; CurrentUser means it applies to your account only and needs no admin rights. Then check what actually took effect:

    Get-ExecutionPolicy -List

    Look at the MachinePolicy and UserPolicy rows. If either shows anything other than Undefined, your IT department sets this centrally and your change is ignored no matter what the command reported. Show the exact output to the instructor; this may need IT support.

2 · Install the core tools

  1. Git tracks changes to files and fetches the course repository. It also installs Git Bash, which provides the fallback Goose installer path used later in this clinic.

    Open the official Git for Windows download page and download the current x64 Setup installer. Open it, approve the elevation prompt, and accept the defaults. If it asks whether to install for your account or everyone on the machine, choose everyone so the other tools can find Git at its standard path.

    You will still type the course commands in PowerShell. Git Bash is a dependency; you only open it yourself if the Goose installer needs its fallback path.

  2. Node runs JavaScript outside a browser. Open the official Node.js download page. Choose LTS, Windows, x64, and the Installer (.msi). Do not choose Current; n8n supports the LTS line used by this course.

    Open the installer, approve the elevation prompt, and keep the default option that adds Node to PATH. On the final screen, leave Automatically install the necessary tools unchecked. That optional Node add-on installs Python and a large Visual Studio build toolchain for compiling native modules; the course does not need that toolchain.

    If you already selected that option and it installed Python 3.14, nothing is wrong. The next step detects the working Python and tells you to skip a second installer.

  3. First refresh this window's copy of PATH, then check whether Node's optional tools or an earlier setup already installed a working interpreter:

    $env:Path = @(
  [Environment]::GetEnvironmentVariable('Path','Machine')
  [Environment]::GetEnvironmentVariable('Path','User')
) -join ';'
$python = Get-Command python -ErrorAction SilentlyContinue
if ($python) {
  python --version
  if ($LASTEXITCODE -eq 0) {
    python -c "import sys; print(sys.executable)"
  } else {
    'Install Python 3.14 before continuing.'
  }
} else {
  'Install Python 3.14 before continuing.'
}

    If you see Python 3.14 and an interpreter path, keep it and do not install a second copy. A path under \WindowsApps\ can be legitimate when the current Python Install Manager owns the alias.

    If the block says to install Python, check whether WinGet is available with winget --version. If it prints a version number, run this one command:

    winget install --exact --id Python.Python.3.14 --source winget --accept-package-agreements --accept-source-agreements

    If WinGet is unavailable or blocked, open the official Python releases for Windows, download and open the current Python Install Manager — Installer (MSIX), and select Install. Then run py install 3.14 in PowerShell. If py is not immediately available, open a new PowerShell window and run that command there. The MSI package is for managed deployment; do not choose it unless your IT team directs you to.

3 · Git and the course repo

  1. The installers record new programs in a Windows setting called PATH, but a terminal reads PATH only when it opens. Your current window may insist a tool is missing even when installation worked.

    Use this rhythm for the rest of the clinic: install, close, reopen, verify.

  2. git --version
Test-Path "C:\Program Files\Git\bin\bash.exe"

    You want a version number and True. Keep this path for the Goose installer fallback later in the clinic.

    If Test-Path returns False, Git installed for your user only rather than machine-wide. Check the other location; whichever returns True is the real path:

    Test-Path "$env:LOCALAPPDATA\Programs\Git\bin\bash.exe"

  3. Create the course workspace first:

    New-Item -ItemType Directory -Force -Path "$env:USERPROFILE\Documents\HarnessBootcamp" | Out-Null

    Then clone the course into it:

    cd "$env:USERPROFILE\Documents\HarnessBootcamp"
git clone https://github.com/TheHolofex/AI_Harness_Bootcamp.git
cd AI_Harness_Bootcamp

    The instructor keeps this repository public during the bootcamp, so the clone should not ask you to sign into GitHub. It returns to private after the bootcamp. If Git asks for credentials during the clinic, stop and show the instructor instead of creating an account.

    The clone holds the exercises, the mission data you will use after the clinic, and the optional transfer-planning file.

4 · Verify Node.js and Python

  1. node -v
npm -v
python --version

    All three should answer with version numbers. Node should be the current LTS release from step 12. The course checks the commands it needs instead of accepting or rejecting one Node version number. If node or npm does not answer, open Settings → Apps → Installed apps, uninstall Node.js, and run the LTS installer from section 2 again.

    If Python is missing, return to step 13. If npm fails with "npm.ps1 cannot be loaded because running scripts is disabled", go back to step 10. That error is the execution policy, not a broken Node install.

  2. Check the interpreter itself rather than judging it only by the command path:

    python --version
python -c "import sys; print(sys.executable)"

    The first command must print Python 3.14, and the second must print the path to an installed Python interpreter. A Get-Command python result under \WindowsApps\ can now be legitimate when the Python Install Manager owns the alias; that path alone is no longer evidence of the old Store placeholder.

    If python opens the Store or is not found, run py --version. If py works, open Settings → Apps → Advanced app settings → App execution aliases and make sure the aliases for Python (default) and Python install manager are enabled; toggle them off and back on to refresh them, then reopen PowerShell. If neither python nor py works, return to step 13.

Phase 2 · Connect your two API keys

5 · Your two API keys

  1. Open Your API keys and read it once through. It covers what a key is, what each one drives, and what to do if one leaks.

    The provider split is simple: OpenAI stays inside Codex, while xAI drives every other cloud harness. Read the reference before you place either key.

  2. Confirm the OpenAI key starts with sk-proj-, then keep it ready for the Codex sign-in step. Do not paste it into PowerShell and do not create OPENAI_API_KEY. Codex stores this key through its own sign-in screen, and no other course harness should be able to select it.

  3. $key = Read-Host 'Paste XAI_API_KEY'
[Environment]::SetEnvironmentVariable('XAI_API_KEY', $key, 'User')
$env:XAI_API_KEY = $key
$key = $null

    This key drives OpenCode, Pi Agent Core, goose, and the AI step in n8n. Check it starts with xai- before you paste — mixing up the two keys produces an authentication error that rarely names the real problem.

  4. The course uses xAI's grok-4.5. OpenCode, Pi Agent Core, and Goose reuse this model id, so save it once instead of editing later commands.

    Codex does not use this variable. Its model is fixed separately to gpt-5.6-terra.

    $env:HB_XAI_MODEL = 'grok-4.5'
[Environment]::SetEnvironmentVariable('HB_XAI_MODEL', $env:HB_XAI_MODEL, 'User')

    This sets the value for this window and every new window. The HB_ prefix keeps the course pin separate from settings a tool reads on its own.

  5. Close the terminal, open a new one, and run:

    'XAI_API_KEY' | ForEach-Object {
  '{0}: user={1} session={2}' -f $_,
    ([string][Environment]::GetEnvironmentVariable($_,'User')).Length,
    ([string](Get-Item "env:$_" -EA SilentlyContinue).Value).Length
}

    One line with two matching non-zero numbers proves the xAI key is saved and available. This prints only its length, never the key, so it's safe to run on a shared screen.

    user=0 means it didn't save — re-run that key's step and check the variable name for typos. session=0 means this window is older than the variable; open another one.

    The model id is not secret, so check it by eye in the same window:

    'HB_XAI_MODEL' | ForEach-Object {
  '{0} = {1}' -f $_, [Environment]::GetEnvironmentVariable($_,'User')
}

    It should read grok-4.5. If it does not, go back one step — OpenCode, Pi Agent Core, and Goose depend on this value.

6 · Your smoke folder

  1. New-Item -ItemType Directory -Force -Path "$env:USERPROFILE\Documents\HarnessBootcamp\prework-smoke"

    Each harness below writes one uniquely named file here. By the end of the clinic you'll have four files side by side in Explorer. The file on disk—not the tool's claim that it wrote one—is the verification that installation worked.

Phase 3 · Install and verify the course harnesses and tools

7 · Codex — your home for the week

  1. This is the one app-install action for Codex. If ChatGPT already opens and its top-left switcher includes Codex, keep that installation and continue to the next step.

    Codex isn't a separate download. It's a mode inside the ChatGPT desktop app, sitting alongside Chat and Work. When this course says the Codex app, that's what it means.

    Use the web installer at get.microsoft.com/installer/download/9PLM9XGG6VKS. Open the downloaded installer and follow its prompts.

    The package is Store-signed, so Store components may flash past while it installs. You don't need to browse the Store yourself, and you don't need a Microsoft account.

    If your laptop blocks Microsoft's distribution service entirely, there's a direct package — see When something breaks at the end. Unlike the rest of this stack, there's no second vendor to fall back on, so tell the instructor when you see the block.

  2. Launch the app. You'll land on a signed-out screen whose main button offers to sign in with a ChatGPT account — which you don't have and won't use.

    Choose Sign in another way instead, paste your OpenAI key, and select Continue.

    Do not create OPENAI_API_KEY for the course. Codex uses the key you paste here, while every command-line harness reads XAI_API_KEY. Keeping those paths separate prevents accidental OpenAI use outside Codex.

    Open the profile menu once. It should report that you are authenticated with an API key. If it names a ChatGPT account instead, log out from that menu and repeat this step using Sign in another way.

  3. Set the two course-wide Codex defaults now: API-key sign-in and the lower-cost Terra model.

    $cfg = "$env:USERPROFILE\.codex\config.toml"
New-Item -ItemType Directory -Force -Path (Split-Path $cfg) | Out-Null
$keep = @(if (Test-Path $cfg) { Get-Content $cfg | Where-Object { $_ -notmatch '^\s*(forced_login_method|model)\s*=' } })
Set-Content -Path $cfg -Value (@('forced_login_method = "api"', 'model = "gpt-5.6-terra"') + $keep)

    Restart the app afterwards so it reads the change. forced_login_method = "api" keeps Codex on the course key. model = "gpt-5.6-terra" keeps new tasks on Terra instead of the more expensive Sol model or another visible default.

    Four lines rather than one, because of how this file is shaped. A line like [windows] opens a table, and every plain setting below it belongs to that table. Appending either course setting to the bottom could silently put it in the wrong table. These commands rewrite both settings at the top, above every table, and preserve the rest of the file.

  4. After the restart, open ChatGPT from the Windows Start menu and select Codex from the top-left switcher if needed.

    Choose Open project and pick the smoke folder you made in section 6: Documents\HarnessBootcamp\prework-smoke.

    Click New chat. A blank chat does not appear in the sidebar until you send its first prompt, so you will rename it after the proof request in step 30.

    Confirm the model picker says gpt-5.6-terra. If it says Sol or another default, select Terra before you send the smoke-test prompt.

    The folder you open is the boundary. Codex reads and writes inside it and has to ask before reaching anywhere else on your machine.

    That's worth pausing on, because it's the shape of everything you'll do this week: you decide what the machine can see before you give it work, not after.

  5. Beneath the message box is a permissions control. Set it to Ask for approval.

    Don't skip this one. That setting is what switches the Windows sandbox on — the boundaries limiting which files Codex can change and whether it can reach the network. Left alone, you get a capable assistant with none of the guardrails the rest of the week assumes.

    The first time it runs, the app builds that sandbox and asks for an administrator prompt. Approve it: that's the stronger elevated sandbox, and it's the one you want.

    If your laptop refuses the elevation, or you see an error mentioning 1385, Codex can run with weaker but workable boundaries. Add this to the bottom of the same config.toml, in a text editor — it is file content rather than a command to paste into PowerShell:

    [windows]
sandbox = "unelevated"

    That is a table header, so it has to be the last thing in the file — everything below it belongs to the table, which is the trap the previous step describes. If you later re-run that step's four-line command, it rewrites the top of the file and leaves this table where it is.

    Check which of the two modes you ended up on. Knowing your own boundaries matters during the week, and it comes up directly on Tuesday.

  6. In the new smoke chat, ask for the file in plain language:

    Create a file named from-codex.txt in this folder containing exactly the text: codex works

    Send the prompt. Once the chat appears in the sidebar, open its … menu, choose Rename, and enter B0 — Codex Smoke Test. Then approve the write when it asks — that prompt is the sandbox doing its job. Open the folder in Explorer and look.

    You want the file on disk, containing codex works. A confident "I've created that for you" with nothing in the folder is a fail, and noticing the difference is the first operator habit this course builds.

    If it can't authenticate, the key is the problem rather than the sandbox — return to Sign in with your API key.

  7. Worth reading once now, so nothing surprises you mid-week.

    Your OpenAI API key runs all of the app's local work, which is the whole course: projects, worktrees, code review, skills, scheduled tasks, the built-in browser, and the permission modes you just set. Every required Codex task uses gpt-5.6-terra.

    It does not unlock the cloud half of the product. Codex cloud, Sites, GitHub and Slack delegation, and voice all need a ChatGPT subscription, and you'll see them greyed out or absent. Nothing in this course needs them, so that's information rather than a problem — but if a tutorial online tells you to click something you can't find, this is usually why.

8 · OpenCode — your second engine

  1. On Tuesday afternoon in P3, Codex calls OpenCode as a single headless job to run one merge on a second model, so you can compare two merges of the same evidence and say where the stronger model actually belongs.

    The two share neither product nor model family: OpenCode runs Grok 4.5 through your xAI key while Codex runs GPT-5.6 Terra through OpenAI. That difference is the whole point — a second opinion from the same family is not a second opinion.

  2. The tested version is in the command itself. You do not need to check the instructor's screen or look up the newest release:

    npm install -g opencode-ai@1.18.11

    Don't use the curl install command from OpenCode's website. That script is written for Mac and Linux shells and can't run on plain Windows PowerShell. There's no PowerShell version of it published, so the equivalent address just returns an error page.

  3. opencode --version

    This must print 1.18.11. If it prints anything else — higher or lower — an older install is probably still on PATH, or another install channel was used. Use the OpenCode reset under Uninstall and start fresh, then rerun the pinned install command.

    Keep that version on screen while you verify the model list. Knowing exactly which build you're on is what makes Tuesday's comparison meaningful.

  4. OpenCode picks up XAI_API_KEY from your environment on its own — there's no login step.

    opencode models xai --refresh

    You should get a list of Grok models in xai/… form. Confirm xai/grok-4.5 appears. If it does not, stop before the proof run and show the instructor the model list.

    An empty list means this window can't see the key. Open a new terminal and try again; if it's still empty, re-check step 23.

  5. This uses the xAI model id you saved in phase 2:

    cd "$env:USERPROFILE\Documents\HarnessBootcamp\prework-smoke"

9 · goose — the prepared checked mission

  1. goose is the agent runtime behind Thursday's prepared watch mission. You give it one operational objective. It reads the local evidence, decides what work comes next, updates the watch products, runs the mission checker, and revises when the checker finds unfinished work.

    The install clinic proves the current stable command-line runtime can start and complete one write. In P6, a supported PowerShell launcher prepares the checked mission for you; your work begins with reading and launching that mission, not configuring it.

    The course requires the CLI. Goose Desktop remains optional.

  2. Do this before configuring or installing Goose. The Windows package contains goose.exe, but it relies on Microsoft C++ runtime files supplied by Windows. Without them, Goose can appear installed and then quit with 0xC0000135.

    Download Microsoft’s current x64 runtime

    Open the downloaded installer, approve the Windows prompt, and choose Install. If it offers Repair, choose that instead. Then return to PowerShell and run:

    $vcRuntime = @(
  'HKLM:\SOFTWARE\Microsoft\VisualStudio\14.0\VC\Runtimes\x64'
  'HKLM:\SOFTWARE\WOW6432Node\Microsoft\VisualStudio\14.0\VC\Runtimes\x64'
) | ForEach-Object {
  $item = Get-ItemProperty -LiteralPath $_ -ErrorAction SilentlyContinue
  if ($item -and [int]$item.Installed -eq 1) { $item }
} | Select-Object -First 1
if (-not $vcRuntime) {
  throw 'Microsoft Visual C++ x64 runtime is not installed.'
}
"Microsoft Visual C++ x64 runtime $($vcRuntime.Version) is installed"

    The final line must print an installed version. The later Goose verification proves the executable can actually load it. Do not download individual DLL files from another site, and do not uninstall this shared runtime during a Goose reset.

  3. Do this before installing. By default goose stores secrets in Windows Credential Manager, which fails often enough on managed laptops that its own documentation tells you to decline it. Setting this first means the installer never tries.

    [Environment]::SetEnvironmentVariable('GOOSE_DISABLE_KEYRING','1','User')
$env:GOOSE_DISABLE_KEYRING = '1'

    One quirk worth knowing: goose only checks whether this variable exists, not what it contains. Setting it to 0 or false also disables the keyring. To turn it back on you have to delete the variable entirely.

  4. goose reads XAI_API_KEY from the environment, but it still needs an explicit provider and model. Reuse the xAI model id from phase 2:

    if ([string]::IsNullOrWhiteSpace($env:HB_XAI_MODEL) -or $env:HB_XAI_MODEL -like 'paste *') {
  throw 'HB_XAI_MODEL is empty or still a placeholder. Return to the xAI model step in phase 2, then come back here.'
}
[Environment]::SetEnvironmentVariable('GOOSE_PROVIDER','xai','User')
[Environment]::SetEnvironmentVariable('GOOSE_MODEL',$env:HB_XAI_MODEL,'User')
$env:GOOSE_PROVIDER = 'xai'
$env:GOOSE_MODEL = $env:HB_XAI_MODEL

    The first check stops here instead of silently saving an empty model. The remaining lines keep goose on xAI in this window and every new one. If goose info -v later reports another provider, stop before running work and restore these two values.

  5. The course uses Goose from the Agentic AI Foundation (aaif-goose). Use only this official AAIF installer; older instructions that point to block/goose are stale.

    cd "$env:USERPROFILE\Downloads"
$env:CONFIGURE = "false"
Invoke-WebRequest -Uri "https://raw.githubusercontent.com/aaif-goose/goose/main/download_cli.ps1" -OutFile "download_cli.ps1"
.\download_cli.ps1

    This intentionally follows Goose's current stable release. The clinic records the version that installed, while the P6 launcher confirms that Goose and the prepared mission are ready before it starts any model work.

    The cd matters only because the installer downloads into whatever folder you are standing in, and the last section left you in the smoke folder. Keep that one for evidence files.

    If PowerShell refuses to run the script, use this form instead:

    powershell -ExecutionPolicy ByPass -File ".\download_cli.ps1"

    And if execution policy is locked by your IT department so neither form works, Goose publishes a Git Bash path — you verified Git Bash in step 15. Open Git Bash from the Start menu and run:

    export GOOSE_BIN_DIR="$HOME/.local/bin"
export CONFIGURE=false
curl -fsSL https://github.com/aaif-goose/goose/releases/download/stable/download_cli.sh | bash

    Note the GitHub address in all three installer commands. The project moved to aaif-goose, and older instructions pointing at block/goose will either fail or fetch a stale build. Current documentation lives at goose-docs.ai.

  6. The installer drops goose into %USERPROFILE%\.local\bin but doesn't add that folder to PATH — it only prints a warning that's easy to scroll past.

    $bin = "$env:USERPROFILE\.local\bin"
$userPath = [Environment]::GetEnvironmentVariable('PATH','User')
if (($userPath -split ';') -notcontains $bin) {
  [Environment]::SetEnvironmentVariable('PATH', "$userPath;$bin".Trim(';'), 'User')
}

    The if makes this PATH step safe to rerun during troubleshooting. PATH is a list you append to, not a value you set, so without the guard running it twice leaves the folder listed twice. Note that this reads and writes your user PATH only; it never touches the system one.

    Then close and reopen the terminal.

  7. $gooseCommand = Get-Command goose -CommandType Application -ErrorAction Stop
$gooseVersion = & $gooseCommand.Source --version 2>&1
$gooseExit = $LASTEXITCODE
if ($gooseExit -ne 0) {
  if ($gooseExit -eq -1073741515 -or $gooseExit -eq 3221225781) {
    throw 'Goose could not start because a required DLL is missing (0xC0000135). Return to the first setup step in this Goose section and install or repair the Microsoft Visual C++ x64 runtime.'
  }
  throw ('goose --version failed with exit code {0}: {1}' -f $gooseExit, ($gooseVersion -join ' '))
}
$gooseVersion
$gooseInfo = & $gooseCommand.Source info -v 2>&1
$gooseInfoExit = $LASTEXITCODE
if ($gooseInfoExit -ne 0) {
  throw ('goose info failed with exit code {0}: {1}' -f $gooseInfoExit, ($gooseInfo -join ' '))
}
$gooseInfo

    You should see the installed Goose version, then provider xai and model grok-4.5. Keep the version with your clinic notes so staff know which stable build you tested. If the block stops, keep the exact error: it separates a broken install or missing Windows runtime from a provider or model problem.

  8. cd "$env:USERPROFILE\Documents\HarnessBootcamp\prework-smoke"
$env:GOOSE_MODE = "auto"
goose run --no-session -t "Create a file named from-goose.txt in the current directory containing exactly the line: goose works"
Get-Content .\from-goose.txt

    auto lets this one-file proof finish without pausing for each action. --no-session keeps the install check from leaving a practice session behind.

Uninstall and start fresh

Use this section when a repair has left one tool in an uncertain state. Most resets take 5–15 minutes; Node, Python, and n8n can take longer. Reset only the tool that failed, then return to the named install step.

Keep application files separate from your work Uninstalling an app should not delete the course repository, an Obsidian vault, n8n workflows, agent sessions, or settings without a separate decision. The commands below move user data to a dated backup when a clean state requires it. They remove only named packages, executables, folders, or environment settings.

Course folders and xAI settings

A failed smoke test rarely needs an app uninstall. Archive the smoke folder, recreate it, and rerun only the affected proof:

$smoke = "$env:USERPROFILE\Documents\HarnessBootcamp\prework-smoke"
if (Test-Path -LiteralPath $smoke) {
  $stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
  Move-Item -LiteralPath $smoke -Destination "$smoke-backup-$stamp"
}
New-Item -ItemType Directory -Force -Path $smoke

To remove the two course-wide xAI settings and enter them again in phase 2:

'XAI_API_KEY','HB_XAI_MODEL' | ForEach-Object {
  [Environment]::SetEnvironmentVariable($_, $null, 'User')
  Remove-Item "Env:$_" -ErrorAction SilentlyContinue
}

This does not revoke a leaked key. Revoke and replace a leaked key in the provider console, then save the replacement in phase 2.

Only if needed · Troubleshooting

  1. Close every terminal and open a new one. That's the answer roughly nine times in ten, and it applies to every tool here.

    If a second new window doesn't fix it, the installer didn't update PATH. Find the program's folder — usually %USERPROFILE%\.local\bin — and add it:

    $bin = "$env:USERPROFILE\.local\bin"
$userPath = [Environment]::GetEnvironmentVariable('PATH','User')
if (($userPath -split ';') -notcontains $bin) {
  [Environment]::SetEnvironmentVariable('PATH', "$userPath;$bin".Trim(';'), 'User')
}

  2. Before assuming an install is broken, confirm the terminal:

    $PSVersionTable.PSVersion

    A version number means PowerShell, which is what every command here expects. An error means you're in Command Prompt or Git Bash, and the command was never going to work.

    See the table in step 8 for the prompt each one shows, and the three error messages that specifically mean "wrong window."

  3. That's the execution policy from step 10. Re-run it, then check Get-ExecutionPolicy -List.

    If MachinePolicy or UserPolicy shows anything but Undefined, IT controls this centrally and you can't override it — ticket them with the exact output. As a stopgap for npm specifically, the same commands work from cmd.exe, which ignores this policy: cmd /c npm install n8n -g.

  4. For OpenCode or Goose, first check that XAI_API_KEY is set in this window (step 23), starts with xai-, and that the command names the xAI provider. n8n uses the same xAI key through its own credential screen.

    Codex uses the OpenAI key you pasted into Sign in another way, not an environment variable. Check the profile menu — it should say API key, not an account. If it's wrong, log out there and redo step 26.

    If Codex keeps pushing you toward a ChatGPT login or opens on the wrong model, confirm forced_login_method = "api" and model = "gpt-5.6-terra" sit in %USERPROFILE%\.codex\config.toml above any [table] header. Re-running step 27's four-line command puts both there safely; restart the app afterwards.

    If a tool worked earlier and now fails with a 429 or a quota message, the key has hit its spending cap. That's not something a reinstall fixes — tell the instructor which key and command produced the error.

  5. Some managed laptops block Microsoft's app-distribution service. The ChatGPT desktop app ships only as a Store-signed package, so unlike everything else in this stack there's no second vendor to fall back on.

    The rescue is the package itself. Download ChatGPT-x64.msix and install it directly:

    Add-AppxPackage .\ChatGPT-x64.msix

    If that's blocked too, it's an IT ticket rather than something you can solve from your seat. Tell the instructor and capture the exact policy error so the ticket has useful evidence.

  6. Believe the folder, not the chat. Check you're where you think you are with Get-Location, and list it with Get-ChildItem.

    If the tool insists and the file genuinely isn't on disk, that's a real defect worth reporting — it has been a live issue on OpenCode for Windows. Show the instructor the tool, its version, and the exact wording.

  7. Stop and ask an instructor with the step number, the exact error text, and what you've already tried. Move on to the next section while the blocker is investigated — most of these are independent, so one blocked tool doesn't block the rest.

    Show the instructor the exact error and what you already tried so the next check starts from the same facts.
