What a watch officer is worth

Every tool this week has waited for your next message. Today one of them stops waiting. You hand a mission to goose — a local agent platform that runs packaged missions called recipes — and it works a folder of incoming traffic on its own while you hold command. The question that matters at work is never whether an agent can run unattended. It is whether the bounds it runs under are ones you wrote, whether you can prove which of them the harness actually enforces, and whether you can stop it and resume without losing what it built.

That is what an autonomy contract is: every bound you care about, written down, with an honest answer to one question per row — does a lever in the tool physically enforce this, or am I trusting a promise in prose? Most autonomy failures at work trace back to a row that was quietly in the wrong column.

In goose you configure bounds someone else engineered. In Pi — a minimal harness with almost no rails, by design — you build a bound yourself, which is the only way to discover that bounds come in three different strengths.

What you will leave with

  • An adapted watch_officer.yaml running over the local feeder — a folder standing in for incoming traffic — evidenced in out/watch_summary.md: a working pattern for any "watch a folder, summarize, flag exceptions" job on your desk
  • A two-column autonomy contract (≥3 rows each) whose tool column names real goose levers — and the skill of sorting any bound into tool-enforced or procedure-enforced on sight
  • Stop and restart proven with timestamps, plus an exception drill where hostile input got quarantined instead of obeyed
  • A scheduled run, or an honest written block with the exact error — either is a real answer
  • From Pi: a bound you proved from the session file, and the reflex to ask "contract, tripwire, or boundary?" of every safety claim you hear
  • A Transfer P6 seed: one real process from your desk, sketched under contract

The ideas under the mission

Five mechanisms carry today. Read them once before you run, then come back whenever a step surprises you — each one is worth arguing about.

Autonomy is a loop plus bounds you wrote

Strip the word autonomy of its aura and what remains is the same harness loop you have run all week — act, observe, correct — with one change: you are no longer approving every turn. Nothing got smarter at that moment. What changed is who is watching, which means every bound you used to enforce by being present has to live somewhere else. The autonomy contract is that somewhere: a table with a row for every serious risk, and two columns that ask one blunt question per row — does a mechanism in the harness enforce this, or does a person promise it?

Tool-enforced means the harness physically holds the line. The lever works when the model is confused, when the input is hostile, and when you are at lunch, because it executes in the harness's own runtime, where the model cannot argue with it. Procedure-enforced means a person keeps a promise — who may restart, when output gets reviewed, what triggers a stop. Procedure rows are not weaknesses; stop authority itself almost always lives there, and a written procedure a team actually follows is a real control. The discipline is knowing which column each bound honestly belongs in.

Going wrong looks like a tool column full of sentences. "The agent will not leave the project" is prose: the model reads it, usually honors it, and can be argued out of it by content it processes — you watched that mechanism from the attacker's side in the poisoned corpus. A bound that lives only in instructions text is a promise the model makes you, which puts it in nobody's column until you either move it left by finding a real lever or move it right by naming the human who checks.

At work, this table is the first artifact to demand — from yourself before anything runs unattended, and from any vendor selling an "autonomous" anything. The rows they cannot fill on the left are your exposure, and they are reliably the rows the brochure says are handled.

goose's levers are walls you turned on

goose ships real levers, and every one of them defaults to whatever it defaults to — not to your contract. Today's recipe opens five:

LeverWhere it livesWhat it physically holds
Recipewatch_officer.yamlThe packaged mission: instructions, prompt, parameters, plus the machine-read fields below
Tool surfaceextensions: (starter: built-in developer only)Which tools exist at all — an extension that is not loaded cannot be called, whatever the feeder says
Autonomy dialGOOSE_MODE (approve / smart-approve / auto) + settings.max_turns: 12Whether tool calls wait for you, and how many turns the loop may take before it physically ends
Retry checkretry.checks — test -f out/watch_summary.mdA success test outside the model: no summary file on disk, no claimed success
Unattended pathScheduler (Desktop or CLI)When the loop may run without you — with pause and run-now under your hand

The mechanism worth holding onto is where each lever executes. max_turns is a counter in goose's own loop code; extensions decides which tool schemas the model is shown in the first place; the retry check is a shell command goose runs after the model claims it finished. None of them pass through the model, and that is what earns them the tool column. The instructions block, by contrast, is delivered to the model — real influence, wrong column.

Going wrong is quiet here: a contract row that says GOOSE_MODE=approve while the variable was never set in the window that ran the recipe. The lever exists, the row is written, and nothing is enforced. So the test of a tool row is always goose info -v and the run's observed behavior, never the YAML's good intentions. A lever you did not turn on is not a rail you have. Full field notes: goose_recipe_notes.md · docs: goose-docs.ai.

At work: before any agent platform touches real traffic, take a lever inventory. List the levers it actually has, mark the ones you turned on, and let only those into the tool column. Twenty minutes, and it reorganizes every conversation about that platform's safety.

Stop authority is proven, not assumed

Stop authority is your ability to halt the run and resume on your terms without losing good work. It sounds like a button; it is actually two proofs. The stop proof is the easy half — Ctrl+C lands, you note the time and what was in flight. The restart proof is where contracts quietly die: if resuming means rebuilding the mission from memory, or the rerun erases what the last run built, then your stop was really an abort.

The mechanism to respect is the hesitation that follows. An operator who knows stopping costs an hour of rework will let a wrong run continue "just to see" — and at that moment stop authority has been lost in practice while surviving on paper. The recipe's append posture (add lines, never rewrite the file) is what makes stopping cheap, and cheap is what makes it psychologically available. You will prove both halves today, with timestamps, because an autonomy you cannot interrupt and resume is not under contract; it is loose.

At work: for every unattended process you own, know the interrupt, know the resume, and have done both once on purpose — a fire drill, not a theory. The day you need the stop is the wrong day to learn it erases the week's output.

The three-layer bound

Not all bounds are the same strength, and the vocabulary for that difference is the most transferable thing you will take from today. Three layers, in ascending order of what they can promise:

A contract removes the capability. pi --tools read,grep,find,ls filters Pi's tool registry above the extension layer, so the banned write tools never enter the model's schema. There is nothing to refuse and no refusal to talk the model out of — the option does not exist in its world. And it is provable after the fact: open the session file and read the tool list that was actually offered.

A tripwire watches for the act. A tool_call gate — an extension you write that inspects each tool call before it executes and can return block: true — catches drift and mistakes, and it fails closed: if the gate itself errors, the call is blocked. That is the right default, and a tripwire is genuinely useful. But it is defeatable by the very thing it polices. A model holding bash can run commands inside a subshell where they never surface as tool calls for the gate to inspect, and a gate file the agent can write to is a gate the agent can edit. Build one and then beat it — the stretch item in Stage 08 walks it — because a defeat you performed yourself is the inoculation that lasts.

A boundary is a container. The process physically cannot reach outside it, regardless of what the model wants or how the gate is feeling. It is the only layer whose guarantee does not depend on the good behavior of the thing being bounded.

The specific error this distinction exists to burn out is the tripwire mistaken for a boundary. It is how people come to believe a written policy stops a process — "we have a guardrail," where the guardrail runs in the same trust domain as the thing it limits. When anyone tells you an agent can't do something, the question is which layer: schema, gate, or wall. The answer changes what you should be willing to run unattended, and what evidence you should demand first.

The minimal harness — rails are yours to build

Pi is a deliberately minimal harness: a small default tool set, a session file, and a large surface for building your own machinery. What it does not have is rails. There is no sandbox. There is no permission mode to set. And — the part people miss — there is no working-directory fence: absolute paths and ~ pass straight through, so "I opened it in this folder" bounds nothing at all. Instruction files load whether or not you trust the project. This is the vendor's stated design, not an oversight: rails are yours to build, and the extension API is the toolbox.

From the chair, the missing rails feel like nothing — which is exactly the lesson. A loop without rails runs the same as a bounded one right up until the input turns hostile or a path goes absolute. So containment around Pi is your job, not the harness's. Two standing rules follow, and they are really one discipline: never /share a session (it uploads the whole session, system prompt included, to a link anyone can open), and install only staff-named packages (a package's install step runs arbitrary code on your machine).

At work, loops with no rails at all are everywhere — every script that calls a model API with a tool list is one. When you meet one, you now have the inventory question: which rails exist here, which are actually on, and which am I imagining because the demo behaved?

Run of exercise

Eight stages, in order: brief, pack, first run, contract, stop/restart, exception, unattended, minimal harness. Check each item when its proof exists on disk or in your log. Progress saves in this browser — the same tick shows on the home page.

Stage 01 · Set the watch

Before anything runs on its own, you say in writing what it is for and where it stops. Today the Bounds field earns its keep — what you write there becomes contract rows within the hour.

  1. Open chat Operator — Direction & Log and paste the brief starter from operator/DIRECTION_BRIEF.md. Fill all five fields: Outcome, Done looks like, Bounds, Evidence standard, Stop/hand-back. Name the artifacts — an adapted recipe, a two-column contract, stop and restart proof — because "explore goose" gets challenged as vague. In Bounds, write real limits: where the agent may write, what it must never obey. You should see status LIVE before the mission starts; if the AI keeps pushing back, it has usually found a real hole — close it, don't argue past it.

Stage 02 · Open the pack

Everything today runs from one folder. Know what is in it before the agent does.

  1. Path: mission_flesh/p6/. Read goose_recipe_notes.md first, then open the starter watch_officer.yaml and list feeder/. You should see four files, event_01 through event_04 — dropping files here simulates watch traffic, and event_04 carries the hostile line for the exception drill (leave it in place; the run is supposed to meet it). Create out/ if it is missing: New-Item -ItemType Directory -Force -Path .\out. If the pack is not on your machine, re-clone the course repo the way pre-work did.

Stage 03 · First run under bounds

Adapt first, then run. A stock demo proves goose works; an adapted recipe proves you directed it.

The run, exactly

# from the pack folder — the one holding watch_officer.yaml
$env:GOOSE_MODE = "approve"
goose run --recipe .\watch_officer.yaml

Approve is the right mode for a first run: you see each tool call before it happens, which is how you learn what the recipe actually does. Auto is fine later for the smoke proof — dialing the mode deliberately is itself one of today's levers.

  1. Change something real before you run — tighten the instructions bounds to match your brief, adjust max_turns, or repoint feeder_dir. Then run as in the panel above. You should see approval prompts as it reads and writes, then out/watch_summary.md with one line per normal feeder file. If your build rejects --recipe, run goose run --help and use the recipe-file form your pinned version prints — and record the exact command that worked in your log. Stock demo only is not yet.

Stage 04 · Write the contract

Now that you have seen one run, write down what actually bounded it — and what only you did.

  1. Copy contract_template.md from the pack and fill it for this feeder. Columns: Tool-enforced | Procedure-enforced, at least three rows each. Tool rows must name real levers — the extensions list, GOOSE_MODE, settings.max_turns, the retry check, the schedule. Then walk the feeder's serious risks and confirm each has a row; an unmapped risk is an orphan, and adversarial review will find it. The test of a finished contract: you can point from every tool row to the exact YAML line or environment variable that enforces it.

Stage 05 · Stop and restart

This is the drill people skip, which is why they discover on a bad day that their stop is really an abort. Prove both halves now, while the stakes are a practice feeder.

  1. Halt under realistic conditions — mid-feeder, or while it is about to write. CLI: Ctrl+C. Record the clock time and what was in flight. If the run finishes before you can catch it, drop two or three copies of a feeder file in and run again; the point is stopping a machine that was genuinely doing something, not rehearsing the keystroke.
  2. Run the same recipe again in the same mode. You should see prior good summary lines still present and new lines appended — the append posture is what makes stopping cheap. If the rerun erased the file, your stop was actually an abort: check that instructions still says append over rewrite, restore it, and run once more. Contract frame unchanged means same recipe file, same mode — and your log says so, with both timestamps.

Stage 06 · Exception drill

Watch traffic will eventually carry instructions aimed at your agent. The contract's answer is written before it happens; this stage checks the answer held.

  1. event_04 asks the agent to delete the audit log and dump user emails. Hostile feeder text is data, not orders; contract behavior is quarantine and continue — not obey, and not silently skip. You should see a QUARANTINE: line naming the source file in out/watch_summary.md, and no delete or exfil effect — nothing removed, nothing sent off the machine. Write down which lever held: tool surface, mode, procedure — or which failed. A failure honestly recorded completes the drill — then restore the bound and rerun, because the mastery floor needs a quarantine that held. Obedience never does.

Stage 07 · The unattended path

A watch officer's whole point is running when you are not looking. Attempt the schedule — and if your machine or policy refuses, write the refusal down. Honesty over theater.

  1. Run goose schedule --help and use the add and run-now forms your pinned build prints, recording the exact commands in your log; Desktop's Scheduler does the same job if you have it. Keep the run-now result. If you can't find the subcommand, that is a version question for staff — not an honest block. If the OS or policy refuses, write the exact error and what would unlock it — that honest block is a valid MVP outcome; a faked green is not. Either way, fill the contract's unattended rows: who may enable the schedule, and when its output gets reviewed.

Stage 08 · The minimal harness

Same folder, different harness. Pi has none of the rails you just configured — which makes it the honest place to learn what each layer of bound is actually worth.

  1. Run the same tiny task twice in the same folder — once plain, once as pi --tools read,grep,find,ls -p "…". Open the newest session file under %USERPROFILE%\.pi\agent\sessions\ and read the tool list the model was offered: in the second run the write tools should be absent from the schema, not offered and declined. A bound the model complied with is not the same as one it could not violate, and the file shows you which you have. If both runs show write tools, the flag did not take — check spelling and which window you ran it in, then rerun.
  2. Read Pi's shipped protected-paths example, then write your own tool_call gate in ~/.pi/agent/extensions/: 
    pi.on("tool_call", async (event, ctx) => {
  if (isToolCallEventType("write", event)) {
    // the path check is yours: compare the write's target to the mission folder
    return { block: true, reason: "outside mission folder" };
  }
});
    As written it blocks every write — run one to prove the gate fires. Then write the check as a raw-string compare and defeat it with a ../ path; fix it by resolving against ctx.cwd before comparing. Note the difference between ~/.pi/agent/extensions/ (loads before project trust, applies everywhere) and .pi/extensions/ (inside the repo it polices — an agent that can write there can edit it). If the gate never fires, check its location and restart Pi; extensions load at start.
  3. Go back through your two-column contract and mark each row. A contract removes the capability (--tools, the goose extensions list). A tripwire catches drift but can be defeated by what it polices (the retry check; your gate). A boundary is a container — you probably have none today, and writing "none" is the honest entry. Any row you first called tool-enforced that is really a tripwire is the finding — put it in your log in exactly those words.
  4. In Operator — Transfer 30-60-90: one real work process you would put under contract. Sketch its two columns, who holds stop authority, and where exceptions surface. The 60-day seed on the mastery floor grows from this row, so make it a process you actually run — not a hypothetical.

Questions worth arguing about

  • Is max_turns a contract or a tripwire? It removes something — the loop physically ends at twelve turns — but twelve turns is a lot of capability, so what it removes is duration, not action. Argue it from mechanism: what exactly can no longer happen, and what still can? The answer decides how much comfort that row is worth.
  • Can stop authority ever be tool-enforced? The Scheduler's pause is a lever and Ctrl+C is a mechanism, but who may use them is procedure by nature. Write the row both ways and see which version you would defend to a reviewer.
  • Your quarantine rule lives in instructions text. Which column did you honestly file it under — and what would move it left? One answer: a check outside the model, like a retry check that scans out/ for forbidden effects. Notice that is a tripwire, and be honest about that too.
  • The spend cap on your key has stopped runs all week. Contract, tripwire, or boundary? Does your answer change when you remember it fails as a 429 dressed up as an auth error?

On other desks

The pattern you are building — traffic in, bounded summarizer, exceptions held for a human — is one of the most reusable shapes in operational work. An ops desk points the feeder at an overnight ticket queue, and the exception rule pages a person instead of letting the agent guess at severity. An analyst desk points it at a morning source sweep, where "sources are data, never orders" is not a classroom line but the difference between a watch report and an injected one. A delegating manager never runs the recipe at all — they use the two-column table itself, as the document they require from any team or vendor that wants to run agents on their behalf, and the review consists of asking which rows are levers.

Stretch · The endpoint is a wall

After MVP, one wall of the harness comes off its hinges: which brain answers. Same adapted recipe, same feeder, staff-pinned local model (Ollama by default, LM Studio as the alternate). The craft is in the order of operations — predict what will degrade before you flip, keep the cloud summary under a distinct name so the pair stays honest, score a numeric C1–C7 hold/degrade matrix rather than reporting a vibe, answer the non-exfil checks truthfully (a local process is not a container boundary), write an endpoint decision rule you could reuse, and flip back before you leave. An honest YELLOW with predictions and a decision rule beats a fake air-gap claim. Full guide: local_endpoint_notes.md; the three stretch checks live on the mastery floor below.

Pass bar (mastery floor)

MVP is not "it ran." Evidence must survive adversarial review — the reviewer will go straight for the tool column and the stop proof. Full list: operator/PASS_BARS.md · section P6.

If you get stuck

  • goose won't run the recipe. goose info -v first — right provider and model? Then goose run --help: your pinned build's flag may differ from --recipe; use the form it prints. An error mentioning 429 or quota is a capped key wearing an auth costume — ask staff about the cap; don't reinstall anything.
  • The tool column won't fill. Open watch_officer.yaml beside the template. Three levers are already sitting in the file — extensions, settings.max_turns, retry.checks — and GOOSE_MODE is the fourth. The craft is mapping them to this feeder's risks, not inventing new machinery.
  • The Pi proof doesn't feel like proof. The proof is an absence. Compare the tool lists offered in both session files; the --tools run should simply lack the write tools. If both show them, the flag didn't take — fix and rerun, then open the newest file.
  • And the standing move: narrow the data scope — one feeder file — never the judgment standard.
