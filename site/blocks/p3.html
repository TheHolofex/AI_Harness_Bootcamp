What this is worth at work

Task Group MERIDIAN issues its September movement order on 22 August. The order names one primary route for the rotation lift and one contingency. Two corridors exist: AMBER runs north over the Selwyn Bridge; CINDER runs south-west and crosses the river by vehicle ferry.

Name a route that cannot carry the lift and the rotation strands at a crossing. Move to the other one without cause and the group buys a longer corridor, a charter it does not need, and a staging fee. Somebody has to answer, on the 22nd, with what is on file.

What is on file is 104 documents across twelve source types — around 82,000 words and 36,000 rows of table. Nobody reads that. Inside it are four current products quoting a figure that a later signed document withdrew, a standing restriction that was rescinded in June and is still being quoted, two enormous exports where slicing the wrong row reverses the conclusion, and open-source material of a quality you would not put your name to.

You will build a run that answers this question, defends every claim in it against a source, and can be handed to somebody else next month to ask the next version of the same question.

What you leave with

  • A single-agent baseline, saved before anything else runs, and a clear answer at the end to whether the rest of the afternoon beat it
  • Coverage and support measures the run applies itself, rather than a rubric in a document
  • Three search agents on genuinely different routes, each bounded by the surface it was given rather than by instructions it could ignore
  • A search that stops on its own rule and says which rule fired
  • Verifiers that only knock findings down, and a rule where one authoritative contradiction beats any number of failed challenges
  • A merge you directed, run on two models, where confidence can only rise on independent evidence

  • A package that names every input the run needs and carries none of this question's answers

The bounds

One baseline. Three search agents. Two rounds minimum, three maximum. Twelve findings into verification at most. Two verifiers. One merge. One provenance check. One package. A run that wants more than this has not been divided properly.

The corpus is too large to read You will not open it. Agents reach it through one read-only server that lists, searches, reads bounded spans and slices tables. Nothing returns a whole file.
September cannot be observed in August The exports stop at the decision date. Everything about the rotation window is precedent or forecast. An answer that claims to have read September readings has read nothing.
Everything here is invented Exercise NORTHWIND SHELF, Task Group MERIDIAN, and every organisation, person, place and event in the corpus. Every file carries a synthetic marker.

The ideas doing the work

Five ideas carry this work. Read them once now, and come back when a result surprises you — the reason will be one of these.

More agents is a cost before it is a benefit

Every agent you add buys coordination, context and waiting before it returns anything. So the honest way to find out whether fanning out was worth it is to have something to compare against, and the only useful comparison is one agent doing the same job. That is what the baseline is for.

It has to be saved before you write the measures, and left unread until the end. Read it first and you will know what the single agent missed, and the measures you write next will quietly be the ones that reward finding exactly that. The point of measuring is to be told something you did not already decide.

The result that ends this honestly is: here is what the fan-out found that one agent did not. If the answer is "nothing much," that is a finding about this job, not a failure of yours — and it is worth more than a run that was merely busy.

You cannot measure recall here, so do not pretend to

Recall is the share of the relevant material you found. Computing it needs a known set of everything relevant in the corpus. Nobody has one — building it would mean reading all 104 files, which is the work you are trying to avoid. A measure you cannot compute is a measure you will end up estimating, and an estimated measure tells you what you already believed.

What you can compute is coverage — the decision names things an answer has to settle, and each is either addressed or openly left open — and support, which is whether a finding you kept rests on a source that actually carries it. Both are countable without knowing the right answer in advance. Both would read differently if the decision were different, which is the test of whether a measure is doing any work.

Different routes means different reading, not different answers

The obvious test of whether your agents searched differently is whether they came back with different things. It is the wrong test. Two agents landing on the same important fact by different paths is corroboration — one of the more valuable things a fan-out produces — and treating it as waste teaches you to prize novelty over truth.

Judge the routes by what went in: which files each opened, which entities each chased, which time windows each covered, what each was forbidden. If those are the same, the routes were never different, however different the returns look.

And a boundary written into an agent's instructions is a boundary it may ignore. A boundary built into the surface it was handed is one it cannot. That is the same distinction you drew this morning between advice and code that runs anyway, arriving on a different surface.

Refuting is not voting

A verifier's job is to knock a finding down against the sources. It adds nothing. Findings survive the attempt or they do not — and the arithmetic is not democratic. One current, authoritative source that contradicts a finding kills it, however many challenges the finding survived. Ten agents failing to refute something is ten agents failing, not evidence.

This corpus punishes the opposite instinct hard. Four current planning products quote one figure for the bridge; one later signed document from the issuing authority withdraws it and gives another. Count the sources and you get the wrong answer confidently. The later, signed, authoritative one governs, and being outnumbered four to one is not an argument.

The other half of that discipline: surviving a challenge is not being true. It means nobody managed to knock it down with what they had. Anything downstream that upgrades "survived" into "proved" has laundered the finding, and the merge is where that usually happens.

A gate can prove a quote exists; it cannot prove it supports you

A provenance check walks every claim back to a source and fails the run when one cannot be walked. What it can establish is mechanical and worth having: that the file exists and is still served, that it is the one cited, and that the quoted words are in it.

What it cannot establish is whether the source means what your claim says it means. That is judgment, it stays with you, and the danger is not that the gate fails to do it — it is that a green gate reads as though it did. A run reporting "provenance PASS" beside a claim its source does not actually support has told you something true in a way that misleads. Keep the two apart in the output, and say which is which.

Stage 02 · Put the measures into the run

Measures belong where the run applies them, not in a document you consult afterwards. A finding either meets them or it does not, and the run should be able to sort by them without you.

Start a new chat named P3 — Run, same project and model, then paste:

Read need\INFORMATION_NEED.md. Do not read need\corpus yet and do not open
anything under baseline\.

Write measures\measures.md defining two measures for this decision.

COVERAGE. The need lists what an answer has to settle. Turn each one into a
numbered obligation, worded so a finding either addresses it or does not.
Coverage is obligations addressed over obligations total, and an obligation
openly recorded as unresolved counts as addressed - a known gap is a result,
an unnoticed gap is a failure.

SUPPORT. For a finding to be kept it must name a corpus file and quote the
words in it that carry the claim. A finding with no quote, or a quote that
does not appear, is dropped rather than flagged.

Do not define recall. Computing recall needs a known set of everything
relevant in this corpus and no such set exists; a measure that cannot be
computed will be estimated, and an estimate here is my own prior opinion
wearing a number.

Then write measures\score.md: how the run reports coverage and support at the
end, as counts I can check, with no adjectives.

Read what came back before you go on:

  1. Every obligation traces to a line in INFORMATION_NEED.md — no invented ones
  2. Each is worded so two people would agree whether a finding addresses it
  3. Support is a mechanical test, not a judgement about quality
  4. Neither measure needs a list of right answers

The test that matters: would these measures read differently if the decision were about something else? If they would work unchanged for any research question, they are not measuring this one.

Stage 04 · Let the run decide when it is done

Two ways to finish: nothing new came back, or the ceiling stopped you. Both are legitimate. What is not legitimate is a run that cannot say which happened.

Paste this into P3 — Run:

Run further search rounds under these rules, written to ledger\stopping.md
before the next round starts:

- A finding is NEW if no kept finding already cites the same file for the same
  obligation. Restating a kept finding in different words is not new.
- Minimum two rounds. One empty round straight after the first pass is a slow
  start, not saturation.
- Maximum three rounds, and at most twelve kept findings in total.
- Stop when a round returns nothing new, or when the ceiling is reached.

At the end write ledger\terminal.md naming which rule fired: SATURATED, or
BUDGET_EXHAUSTED with the obligations still unresolved listed by number.

BUDGET_EXHAUSTED is a real ending and I would rather have it than a run that
pretends the ceiling was saturation. Do not pad findings to reach twelve, and
do not drop good ones to stay under it.

What you should see. A terminal record naming one rule, and at most twelve findings. If it stopped on the ceiling, the unresolved obligations are listed — that list is part of the answer, not a defect in it.

When it does not. A run reporting SATURATED after two rounds with obligations still untouched has defined "new" too loosely. Tighten it to file-plus-obligation and rerun the last round.

Stage 05 · Verifiers that only refute

Two agents, each taking half the findings, each trying to knock them down. They add nothing. This is where a corpus that rewards counting sources will punish you.

Paste this into P3 — Run:

Split the kept findings between exactly two verifier agents. Each gets half
and never sees the other half.

A verifier may use the northwind_evidence tools and nothing else. Its only job
is to defeat the finding it was given. It adds no findings of its own and
proposes no rewording.

Disposition rules, and they are not a vote:
- One current, authoritative source that contradicts a finding DEFEATS it,
  regardless of how many challenges that finding has already survived.
- Where two sources conflict, the later one from the issuing authority
  governs, and an explicit withdrawal of an earlier figure settles it.
- Repetition is not authority. A figure appearing in four products and
  contradicted by one later signed document loses.
- A finding nobody could defeat is recorded as SURVIVED, never as PROVED.

Write verify\dispositions.md: every finding, its verifier, SURVIVED or
DEFEATED, and for each defeat the source that did it and the quoted words.
Preserve defeated findings in the file - I want to see what died and why.

What you should see. Some findings defeated, with the source named. If nothing died, the verifiers were being polite — check whether they used the tools at all, or simply reread the findings and agreed with them.

Watch for the trap. Somewhere in this corpus a figure appears in several current documents and is withdrawn by one later signed one. If your dispositions kept the popular figure, the rule was applied by counting rather than by authority, and that single error changes the answer.

Stage 06 · Merge under a stated rule

You write the rule before you see the disagreements. Then you run the merge twice — on two models from different families — and pick the one you ship, for a reason you can point at.

Paste this into P3 — Run:

Write merge\rule.md before merging anything. It states:
- CONFLICT: what happens when surviving findings disagree. Name the conflict
  in the output; do not split the difference.
- WEIGHT: what carries more - later over earlier, issuing authority over
  repetition, observation over marketing, table over prose.
- CONFIDENCE: it may rise only when two sources that do not depend on each
  other carry the same claim. It may never rise because more agents said it.
  Nothing leaves the merge more certain than its evidence.

Then produce merge\answer_terra.md: one decision, answering the question and
settling every obligation in measures.md, each claim citing its file and the
quoted words.

Report the coverage and support counts from measures\score.md.

Now run the same merge on a second model. Paste into P3 — Run:

Run the same merge on a model from a different family, as one headless job.

From the project root, run:

  cd "$env:USERPROFILE\Documents\HarnessBootcamp\P3_Need"
  $merge = (Get-Content merge\rule.md -Raw) + "`n---`n" + (Get-Content verify\dispositions.md -Raw) + "`n---`nApply the rule above to the surviving findings above. Produce one merged decision. Cite the file and the quoted words under every claim. Output the merged decision only."
  opencode run -m "xai/$env:HB_XAI_MODEL" $merge | Out-File -Encoding utf8 merge\answer_grok.md

Capture its output, as above. Do not ask OpenCode to write a file itself.

Then write merge\placement.md: where the two merges differ, which one I ship,
and the reason - which must be something you observed in the two of them, not
a general preference about models.

Why two. Deciding to fan out is half the job; where you put the stronger model is the other half, and the merge is usually where the judgment concentrates. Running it twice is how you find out whether that holds here rather than assuming it.

What you should see. Two merged answers, a stated difference between them, and a choice with a reason attached. A placement.md that says "Terra is better" with no observation behind it is the failure this step is built to catch.

When it does not. If OpenCode reports success but the file is empty, it was asked to write rather than to answer — the Out-File pipe is what keeps the writing on this side. Check $env:HB_XAI_MODEL is set from the install clinic, and run opencode models xai --refresh if the key may not be reaching it.

Stage 07 · A provenance check that fails loudly

Every claim walks back to a source that still serves it, or the run fails. The gate proves the citation is sound. It does not prove the source agrees with you, and the output has to keep those apart.

Paste this into P3 — Run:

Build provenance\check.md as a step that walks every claim in the shipped
merge back through resolve_citation on the northwind_evidence server.

For each claim it records: the file, the quoted words, whether the surface
still serves that path, whether the quote appears, and the file digest.
A claim that fails any of those fails the run.

The report must separate two things and never blur them:
  CHECKED - this surface serves the path, and the quoted words appear in it.
  NOT CHECKED - whether the source supports the claim built on it.

Never print a claim as verified. Print it as cited, and say what that means.

Then run it and report the counts.

Now try to get three bad claims past it. Paste:

Test the gate on three planted claims, one at a time, restoring the file
after each:

1. Add a claim citing a file that is not in the corpus.
2. Take a real claim and alter three words inside its quotation.
3. Take a real claim and repoint its citation at a source the corpus shows
   was superseded.

Report which the gate caught, which it did not, and for any it missed, what
it would have to check to catch it.

What you should see. The first two fail hard — resolve_citation reports the path is not served, or that the words do not appear. The third is the interesting one: a superseded source still exists and still contains the words, so a structural gate passes it. That is not a defect in the gate; it is the boundary of what a gate can do, and the reason that failure has to be caught by the weight rule in Stage 06 and by you.

The thing to take away. A green provenance report beside a claim its source does not support is true and misleading at once. Keep cited and supported in different columns for the rest of your career.

Questions worth arguing about

None of these has one right answer. Each changes what you build, so have the argument before somebody has to live with your choice.

  • The fan-out found little the single agent missed. Was the afternoon wasted? No — you now know something about this job you could only learn by measuring it, and next time you can spend one agent instead of six. The waste would be running the fan-out for a year without ever checking. The uncomfortable version: how many of your current multi-agent habits have never been compared against one agent doing the same work?
  • A finding survives two verifiers. How much is that worth? Less than it feels. It means nobody defeated it with the sources they reached, which is a statement about the verifiers as much as about the finding. The honest phrasing is the one Stage 05 forces: survived, not proved. Watch how strongly you want to upgrade it anyway.
  • Repetition really is evidence sometimes. When? When the repetitions are independent — different people observing separately and agreeing. It is worth nothing when they are copies, and in a document corpus most repetition is copying. The test is not how many say it but how many found out separately, and that is usually harder to establish than the claim itself.
  • The gate passes a claim built on a superseded source. Who is supposed to catch that? The weight rule, if you wrote it well, and you if you did not. It is the clearest example of a check working exactly as designed while the run is still wrong — and of why a green light is not the same as a right answer.
  • Should the package carry a default answer for the obligations it usually settles the same way? Tempting, and it turns a method into a template that confirms itself. The line is between fixing how the question is asked and fixing what comes back. Fix the first, never the second.
  • The ceiling stopped the search with obligations unresolved. Do you ship? You ship the answer with the gaps named — that is what the decision-maker needs on the 22nd. Shipping a complete-looking answer with quietly unaddressed obligations is the only genuinely wrong move here.

The same run on other desks

  • Any recurring due-diligence question: a vendor, a site, a supplier. Several source types, conflicting ages of document, and a decision with a date on it.
  • Incident review: the same shape with logs, tickets and chat as the corpus — and the same trap, where the loudest repeated account outranks the one authoritative record.
  • Any question you are asked quarterly: the second time you answer it from scratch is the signal that the method should have been the deliverable.

If you get stuck

  • /mcp shows no server. Check .codex\config.toml uses forward slashes and absolute paths, that npm ci completed in evidence_surface, and that you fully quit and reopened the app. Run node server.mjs --root "..\need\corpus" --validate-only first — if that fails, the config is not the problem.
  • An agent says a file is not on this surface. That is the boundary working. Either the route was not meant to reach it, or the surface was cut too narrow — decide which before widening anything.
  • A table query returns nothing. Check the identifier column first. A reading from one station or sensor does not transfer to another, and the wrong slice returns an empty set or, worse, a plausible one.
  • Everything about September comes back empty. It should. The exports stop at the decision date. Evidence about the window is precedent and forecast, and an agent insisting on September readings is asking for something nobody could have on the 22nd.
  • The verifiers defeated nothing. Check they used the tools. A verifier that rereads a finding and agrees has not attacked it; give it the sources and the instruction to defeat, not to review.
  • The merge reads like two reports stapled together. The conflict rule is missing or too vague. Name what happens to disagreement before merging again, and require conflicts to appear as conflicts.
  • OpenCode returns nothing. Capture its output rather than asking it to write files. Confirm $env:HB_XAI_MODEL is set, and run opencode models xai --refresh to check the key is reaching it.
  • You want a fourth agent. Write down what it would do that the three cannot, then check whether that is a route or just more of one. Usually it is the second.
