Why this desk exists

Somewhere in a normal work week, a model drafts something you pass upward — a status rollup, an extraction from documents you didn't have time to read twice, a summary that becomes someone else's operating picture. When that draft is wrong, the error arrives wearing your name. The trap is quiet: a model's fluent answer feels like a second opinion because it's phrased like one. It isn't. It's one witness, interviewed once.

The countermeasure is a desk, and you build it now: the same extraction demand, run verbatim through two engines that share neither product nor model family, a comparator that surfaces every place they differ, and a ruling — from you, on evidence — for each one. An engine here means a model running inside a harness product; today's two are the Codex app and OpenCode running Grok on your xAI key. By the end you own the whole circuit, and it reruns on Monday's real work with nothing but a new corpus.

The craft under the desk

Read these once before you start, then come back to whichever idea a disagreement — or a suspicious agreement — puts to work.

Agreement is not truth; disagreement is a sensor

When two engines return the same answer, it's tempting to call the answer confirmed. What a match actually establishes is narrower: two systems produced the same output. If their failure modes overlap, they can match for shared-wrong reasons — and their failure modes do overlap. Both models trained on overlapping public text, both read the exact corpus you handed them, and both are optimized to produce fluent, confident prose. Where the corpus is thin or ambiguous, each fills the gap with the most plausible completion — and the most plausible completion is often the same wrong guess. A match therefore tells you a claim is either well-supported or a shared blind spot, and it cannot tell you which. That is why the claims driving the release decision still go back to their sources even when both engines agree.

Disagreement is the more useful signal, and it's worth being precise about what it is. Two different model families under two different harnesses diverge mostly where the evidence underdetermines the answer — a contradiction between sources, a gap the brief doesn't cover, a synonym the status vocabulary maps two ways. So each disagreement row is a pointer to exactly the claims where mechanical processing ran out and judgment has to take over. That is what the second engine buys for its cost: not a better answer, but a map of where your attention belongs. The comparator lets you spend attention on material splits and the few agreed claims that actually control the release decision, rather than rechecking low-consequence prose.

The failure smell on this idea has a name in the lesson outcomes: “they basically agreed.” If that sentence appears without a table behind it, no comparison happened — an impression happened. The other failure is subtler: treating every split as evidence one engine is defective. Usually neither is defective; the evidence is genuinely thin, and the honest ruling is UNKNOWN with a note saying why.

Independence hygiene — the cargo neither engine declares

For this controlled comparison to support a claim about engine differences, both engines must receive the same frozen job and every material difference in their run paths must be declared. Neither engine helps you with this. The Codex app loads AGENTS.md from whatever folder you open as the project — including the P2 project whose harness you changed — plus %USERPROFILE%\.codex\AGENTS.md, discovered skills, enabled plugins and trusted hooks, project custom agents, memories, and any enabled MCP server's tools or guidance. OpenCode can import Claude-named compatibility files even when no Anthropic key is present. The official guard OPENCODE_DISABLE_CLAUDE_CODE=1 blocks those files; it does not enable or call Anthropic. The cargo is invisible until you inventory it.

Here is what going wrong looks like, because it's the most common way this desk fails: you run the brief inside your P2 project, the Codex output comes back noticeably sharper, and you conclude the Codex app is the stronger engine. That comparison is contaminated: the product and model family changed, but so did the instruction path, so the observed delta cannot be attributed to the engine split. The run is still evidence about the combined setups; it is not clean evidence that one engine is stronger. An advantage you didn't declare looks exactly like a capability you don't have.

The discipline is declare or clear, and either is honest — silence is the only wrong answer. Clear means a fresh folder holding only the frozen corpus, no project skill or custom-agent files, no active MCP server, the Project Organizer plugin's Stop release gate inert in that folder, the compatibility guard set (OPENCODE_DISABLE_CLAUDE_CODE=1), and installed plugins held out of the OpenCode run with --pure. Declare means writing the run identity down like a lab notebook entry: engine, model id, version, folder, instruction files, skills, plugins and hooks, custom agents, memories, and tool surfaces. The comparator's first table exists for exactly this, and it gets filled before any side-by-side row.

The frozen brief is the control

You're about to attribute output differences to the engines. That attribution is defensible only if the brief, corpus files, join rule, and other outcome-relevant conditions outside the named provider-and-model split are held fixed. Any residual difference stays in the run identity as a competing explanation. In experiment terms the brief is the control: the thing held fixed so the remaining variation means something. This is why BRIEF-v1 is frozen and why editing it mid-run is the one move that ruins the afternoon quietly. A clarification you give one engine and not the other converts your comparison into a story about your prompting.

Read the brief once as a piece of engineering and you'll see each rule closing a degree of freedom. WatchIDs must come from watchlist.csv — so the join is deterministic and no model gets to guess which entity a paragraph is about. Status must be one of four values — so synonyms can't blur into unfalsifiable prose. Every factual cell needs a quote of twenty words or fewer — so checking a claim takes seconds, not minutes. Contradictions are kept, not resolved — so the model can't silently pick a side of a dispute that's yours to rule on. Unlisted entities are fenced into their own section — so scope creep is visible instead of woven in. Remove any of these and the comparator fills with noise you can't adjudicate.

An underspecified brief fails differently, and the failure is instructive: both engines drift, but in different directions, and the disagreement count grows. When that happens the divergence is telling you about the brief, not the engines. Keep BRIEF-v1 frozen for this decision, record the ambiguity as a brief finding, and carry the correction into the next real run instead of turning this run into a prompt-tuning exercise.

Apply the presentations: make the connection earn its place

The two MCP presentations own the protocol map. P3 turns that map into five operating decisions attached to a real source packet. A direct file read would be simpler for this tiny, one-time corpus; this connection earns its place by enforcing a reviewed retrieval boundary and leaving a reusable call-and-provenance receipt for the final handoff. At work, if standard access, reuse, provenance, or control does not repay the setup and operating cost, skip MCP.

DecisionP3 answerWhat you inspect or record
FitA bounded, reusable evidence route—not a second opinionThe work goal, why MCP helps, and the direct-access fallback
PrimitiveTwo model-selected read tools under host policy; no resource or promptWhy the requested operation and approval path fit tools

ExitPacket saved, project connection disabled, evidence task closedActual source basenames, exceptions or denials, raw-source checks, and disabled state

The server-wide instructions matter because the host loads them alongside the tool definitions; they are part of the effective contract and a possible trust surface. Descriptions and annotations help the host and model choose and present tools. Input and output schemas constrain shape. None of them proves that the server is honest or that a returned claim is true. The course repository origin and commit establish provenance, local hashes fingerprint the files used in this run, per-call approvals bound authority, and source hashes plus raw-context reading check the evidence.

A useful failure rule is equally concrete: read the visible error, retry only a correctable planned call once after fixing its argument, and stop on a protocol failure, unexpected surface, scope drift, or unplanned network request. Never make a failing connection “work” by widening tools, scopes, or data access, and never report a native read as an MCP result. The fixture suite already tests the artificial failures; class time goes to the evidence product.

Adjudication is a ruling, not an average

When the engines split on a field, three tempting moves are all wrong: ask a third model to break the tie, keep the answer that sounds more confident, or split the difference. All three keep the decision inside model-land, where the error was born. The correct move is shorter than any of them — open the source file. The brief's quote rule means each engine has told you where it thinks its evidence lives; go there and read. Then rule the field: which side wins, why, and what evidence outside either model settles it. Write the ruling in the verdict column. If the sources genuinely don't settle it, UNKNOWN is a ruling too — often the most honest one on the sheet.

If the cited source does not settle a consequential claim, do not manufacture another run. Record what the source supports, what remains missing, and the smallest defensible disposition: qualify it, discard it, or mark it UNKNOWN. The useful result is a decision whose evidence boundary is explicit.

Adjudication done this way produces a specific artifact: a note a supervisor can act on cold, with every ruling walkable back to a file and a line. That's the difference between “the AI said” and intelligence work. On a real desk the rulings are what you're paid for — the engines are interchangeable; the verdict column is you.

Four instruments that look alike

Once you've run a second engine and connected a server, it's easy to blur four different instruments together. A second engine is a different product and model family given the same frozen job. It adds provider-and-model diversity and can expose a failure the first engine does not share. It does not establish whole-path independence; that requires a named failure, evidence that the path capable of causing it is separated, and a record of what remains shared. An MCP server supplies data or capabilities to a host; it improves access, not judgment, and may create a shared dependency across several engines. A subagent is a specialist the Codex app spawns under your commander chat — same product and model family, so it buys division of labor and clean context, not a new provider-and-model path. A second human brings actual judgment and accountability — the one thing none of the machine instruments carries.

InstrumentWhat it buysWhat it cannot do
Second engine (OpenCode)Provider-and-model diversity; another failure surface to compareOwn the verdict; guarantee truth; establish whole-path independence
MCP serverStandard, reusable access to bounded data and capabilitiesAdd another opinion; prove the returned data is true; grant its own authority
Subagent (Codex app)Parallel specialist lenses; keeps the main chat cleanAdd provider-and-model diversity; establish independence from head count
Second humanJudgment and accountability; a potentially different challenge pathScale to every claim; establish independence without disclosing evidence path, role, and incentives

Here is what mistaking one for another looks like: two engines read the same claim through one MCP server and the report calls it “independently confirmed.” It is not. The models differ, but the retrieval path is shared. Three subagents converging has the same naming problem: head count adds no corroborative weight when the product, model family, and cargo remain shared. Whatever mix you run, the merge and every final disposition stay with the operator — MCP server ≠ engine ≠ subagent ≠ human.

MCP choices after this local exercise

SituationUseMinimum operating control
One user, local files or a local processstdio — the client launches a subprocess and exchanges newline-delimited messagesInspect the full command; pin reviewed code; restrict filesystem and network reach; keep diagnostics on stderr
Remote or multi-client serviceStreamable HTTP — each message goes to one MCP endpointHTTPS; OAuth 2.1 when protected; least-privilege scopes; token bound to that MCP server; bearer token in the header, never a prompt or URL
Many servers or hundreds of toolsProgressive discovery — catalog, inspect, then executeKeep inactive servers disconnected; load only relevant tool definitions; preserve per-call approval and cross-server data boundaries
Write, send, delete, buy, or change permissionA narrowly typed tool only when the action is worth delegatingExact arguments visible; server-side authorization and validation; human confirmation; post-action verification and audit receipt

The current MCP specification is dated 2026-07-28 and uses stateless, self-contained requests with no connection-scoped initialize handshake or protocol session. Compatible clients may still use an earlier negotiated revision. P3 is wire-version agnostic: inspect the server's effective surface, real calls, and error behavior instead of assuming a tutorial's flow. P3 keeps writes out of scope so the evidence lane stays clean; P6 is where permission and action boundaries become the main event.

Comparison decisions worth examining

  • If the engines agree on every field, what did the second engine buy you? Possibly nothing on this run. The search record and the evidence behind the release-driving claims show what you inspected; your workplace rule should state when that checking cost is warranted.
  • Which is worse: a wrong claim both engines agreed on, or a disagreement you ruled incorrectly? The first fails silently and scales; the second leaves a trail — your ruling, your reasoning, reviewable. What does that say about where checking effort should go?
  • When is a third engine worth it? Each added engine can add provider-and-model diversity, with diminishing value and linearly growing adjudication cost. Define the claim class and named path separation that would justify that cost.
  • When should a claim remain UNKNOWN? When the available sources do not settle it. Name the missing evidence and the decision that must wait; do not turn model confidence into support.

If you get stuck

  • OpenCode won't run the brief. Read the error body before touching the install: 429 or quota means a capped key wearing an auth-failure costume, and a brand-new key does nothing until its ACLs attach. Neither is fixed from your seat. While you wait, keep working the Codex side and prep the comparator.
  • The engines agree on everything. That's a valid result. First confirm both sides ran clean, then record the fields inspected and source the agreed claims that control the release decision.
  • The comparator is eating the block. You're logging cosmetic rows. Narrow the data scope — fewer fields, material differences and release-driving agreements only — and never the judgment standard. If a concept is what's blocking you, ask the lead to diagram it live, then continue on your own chair.
  • A tool returns isError. Read the tool's message. Correct one planned argument and retry once only if the error is actually correctable. Otherwise record the missing evidence and stop that call; do not widen the allowlist or source scope.
  • The MCP server does not appear or the connection fails. Preserve the visible error. Confirm project trust, inspect the generated TOML, rerun the locked --describe command, confirm server diagnostics stay on stderr, then completely restart the app—in that order. If those checks do not locate the fault, ask the lead to inspect the server/client exchange; do not install an unpinned debugger mid-run. Mark the MCP outcome not yet and finish the real adjudication from the raw files; never pretend a native read came through MCP.
