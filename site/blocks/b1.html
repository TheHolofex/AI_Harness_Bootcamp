Stage 02 · Paste Prompt 1 — build the dashboard

This prompt supplies the complete product specification. It uses all seven example reports from the start, including DELTA_new.md; there is no staged source update in B1.

Copy this entire prompt into B1 — First Light Dashboard:

Read mission_flesh/b1/README.md and every Markdown file in
mission_flesh/b1/reports/, including DELTA_new.md.

Build the finished product now at:
mission_flesh/b1/first_light/index.html

Create a polished, responsive operations dashboard named
“First Light Operations Picture.” It should feel like a high-end operational
product, not a generic admin template.

SOURCE RULES
- Treat all seven report files as the complete provided example corpus.
- Create exactly one canonical embedded data record per source file. The same
  record may appear in the timeline and explorer; do not duplicate it in data.
- Preserve the source wording and qualifiers. Never invent, smooth over, or
  silently resolve a missing, uncertain, or conflicting fact.
- Keep the exact source filename visible in every report detail.
- report_06_export_eu.md has no DTG. Label it “Needs timestamp” and keep it out
  of the chronological sequence instead of guessing a time.
- Use this report-type map:
  report_01_bridge.md → OPS REPORT
  report_02_node_b.md → FIELD NOTE
  report_03_media.md → OPEN SOURCE NOTE
  report_04_restore.md → OPS REPORT
  report_05_convoy.md → MOVEMENT LOG
  report_06_export_eu.md → TICKET FRAGMENT
  DELTA_new.md → LATE INSERT
- The source-backed headline facts are 7 reports, 6 dated, 1 needing a
  timestamp, and a dated window from 0340Z to 0600Z.

DELIVERY
- Create one self-contained HTML file with embedded CSS, JavaScript, and data.
- It must open offline by double-click: no server, framework, package, CDN,
  external font, library, fetch call, or network request.
- Do not modify the reports or anything under operator/.
- Do not create a brief, manifest, release note, log, or planning document.

INFORMATION DESIGN
- Use a restrained dark operations palette, crisp typography, generous spacing,
  and a strong visual hierarchy. Reserve red for the explicitly high-severity
  EU export issue; use status text as well as color.
- Mark the dashboard visibly as “Synthetic training data.”
- Start with a compact command header and four large metric cards: Reports,
  Dated, Needs timestamp, and Time window.
- Make the chronological timeline the main visual story. It must begin with the
  convoy at 0340Z and end with the late insert at 0600Z.
- Give the undated export ticket a prominent separate “Needs timestamp” lane.
- Add a report explorer with full-text search, report-type filter chips,
  Dated / Needs timestamp filters, a live visible-result count, Clear all,
  and a useful empty state.
- Let a user open and close every report to see all available source fields and
  the exact filename.
- Preserve operationally important phrases such as “likely unrelated,”
  “do not amplify,” “Service CLEAR,” and “monitoring elevated 2 hours.”

PRODUCT QUALITY
- Use semantic HTML, visible keyboard focus, sufficient contrast, and controls
  that work by keyboard as well as mouse.
- Make the desktop layout feel composed at 1440 × 900 and stack cleanly at
  390 × 844 with no horizontal scrolling, clipped controls, or unreadable text.
- Use subtle motion only where it improves orientation, and honor reduced-motion
  preferences.
- Make every filter, search action, reset action, detail control, visible count,
  and empty state work with embedded JavaScript.

Do not pause to propose a plan or ask me to choose the design. Make sound design
decisions and build the dashboard now. Before handing it back, verify that the
embedded data has one canonical record for each of the seven source files, dated
events are ordered correctly, the undated report remains explicit, and every
interaction has working JavaScript.
Report the exact dashboard path when finished.

Approve each requested write under mission_flesh/b1/first_light/. Keep the chat open when Codex reports that index.html is complete.

  1. mission_flesh/b1/first_light/index.html exists, and the source reports remain unchanged.
Why this prompt produces more than “make me a dashboard” It fixes five things a vague request leaves open: the source boundary, the truth rules, the information hierarchy, the interactions, and the finish checks. “Beautiful” becomes actionable only after those decisions are named.

Lesson reflection

The useful pattern: the prompt fixed five things before the build began: source boundary, truth rules, information hierarchy, interactions, and finish checks. When an AI-built product is weak, find which of those five is underspecified. P1 will put that judgment in your hands.
