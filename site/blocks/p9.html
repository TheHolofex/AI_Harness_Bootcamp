Change one behavior, then measure the change

Fine-tuning changes a model’s parameters with examples. It can make one stable behavior more reliable, such as a house output format, a classification boundary, or an extraction schema. It is a useful option when the work repeats, the desired result is clear, and you can check the result on new examples.

It is not a way to keep facts current, repair an unclear task, or make private data safe by putting it into a model. Those are different problems, and they need different controls.

Today, the instructor runs one small private adapter job with public Hugging Face data. Your work is to follow the chain of evidence: the data that entered the run, the base-model baseline, the configuration, and the held-out results that support or limit the final decision.

What you will leave with

  • A rule to choose prompting, retrieval, tools, validation, or fine-tuning.
  • A data review list for a training dataset.
  • A hardware map for local preparation, small adapter tests, and cloud training.
  • A run record that identifies data, model, adapter, compute, evaluation, and decision.
  • A path for Linux, macOS, Hugging Face Jobs, and RunPod.

Before the demonstration

  • Carry forward P8’s standard: a model change is an evidence exercise, not a preference.
  • The instructor’s Job, adapter, logs, repository, and tokens stay private.
  • Use only public data or data you have written permission to use.
  • Do not upload personal, organizational, regulated, secret, or unlicensed data to a training service.
  • Bring one candidate behavior from your work, with its input, expected output, and acceptance check.

The ideas

Fine-tuning is one way to change a system. Start with the smallest control that can plausibly solve the problem, then test whether it did.

Use an adapter

The base model is the original model and its original parameters. Full fine-tuning changes many or all of those parameters, which increases the memory, storage, and recovery work. That is rarely the first practical move for a narrow operational behavior.

A LoRA adapter adds small trainable matrices to selected model layers while the base weights stay fixed. QLoRA keeps the base model in a low-bit form during adapter training, which can reduce memory use further. In both cases, the output is an adapter that belongs with a specific base model and configuration.

That separation is useful because it leaves the base model intact. You can attach the adapter only where it passed, compare it directly with the base model, and remove it when the evidence no longer supports its use. An adapter is a controlled change, not a new general-purpose model.

How fine-tuning improves a specific behavior

Fine-tuning does not add a database of facts to a model. It changes the model’s tendency to produce one sequence of tokens rather than another when it sees a particular kind of input. A good training example says, in effect, “when the context looks like this, this answer pattern is the one we want.”

During supervised fine-tuning, the model reads a formatted example and assigns probabilities to the next answer tokens. The training loss measures the gap between those probabilities and the expected assistant answer. Backpropagation then adjusts trainable values in the adapter so that the desired tokens become more likely in similar contexts. Repeating this across varied, correct examples can make the behavior more reliable.

The base model still supplies the broad language and reasoning capability. The adapter supplies a small, task-specific shift. That is why a narrow, clean dataset can help with a stable format or repeated decision pattern, while a noisy dataset, wrong chat template, or inconsistent labels can make the model less reliable in exactly the same way.

Match the method to the learning signal

Supervised fine-tuning, or SFT, is the default. Use it when you have good examples of the exact answer or response form you want. The instructor demonstration belongs here. For prompt/completion data, train the completion rather than the prompt. For conversational data, apply the model’s correct chat template and, where the template supports it, calculate loss on assistant messages rather than on the user or system text.

DPO is a preference method. It needs a credible pair for each prompt: a chosen response and a rejected response. It is useful when the difference between acceptable and preferred behavior is what you need to teach. A pile of ordinary answers is not a DPO dataset.

GRPO is a reward-driven method. It needs a reward you can execute or review with discipline, such as a verifier for a structured result. It introduces more moving parts than this demonstration needs. Do not use it because it is newer; use it only when the reward really measures the result you care about.

LoRA is the default adapter method for each of these paths. Use QLoRA when quantizing the base model makes the run fit the available memory. More advanced choices, such as LoftQ initialization, DoRA, or activated LoRA for specialized adapter serving, belong after a baseline adapter and a valid evaluation set exist. They are not substitutes for better data or a clearer task.

Do not use training loss as the result

Training loss tells you how closely the run fits its training examples. It cannot tell you whether the adapter helps on new work, whether the data leaked answers into the test, or whether the adapter damaged a nearby behavior.

Build a held-out suite before training and keep those cases outside the training input. Then run the base model and adapter on the same cases, under the same prompt, decoding settings, and score rule. This gives the comparison a control instead of a story. If you use a held-out case to pick settings or edit the dataset, retire it from the final suite and replace it with a new unseen case.

Use the table as a reading exercise, not a planning spreadsheet. The right P9 question is: “What does my base model do on my held-out cases, under my exact inference contract?” Your own baseline-versus-adapter table is the only performance evidence that supports a decision for your workload.

Use this sequence

  1. Write a behavior contract that names the input, output, acceptance check, non-goal, and owner.
  2. Build the held-out suite before training. Keep close duplicates, near-duplicates, and template variants in the same split.
  3. Capture base-model results, including raw output, settings, scores, and failure types.
  4. Start with a small model, narrow dataset, short run, and one adapter configuration. Use a fixed seed and record it.
  5. Read the failures before changing settings. Check data fit, format, instructions, tool need, evaluator, model limit, truncation, and role order.
  6. Change one relevant variable at a time, and version the data and configuration for every run. Do not tune on the held-out suite.
  7. Test the intended serving path before release. The chat template, tokenizer, generation defaults, quantization, and adapter-loading path can all change behavior.

Review training data before use

Every training example makes a claim about the behavior you want. Before you admit a dataset, read its card and real rows. Check the license, source, intended use, fields, splits, and revision rather than relying on the dataset name alone.

Look for duplicate prompts, boilerplate answers, wrong languages, personal data, hidden instructions, biased labels, and content that does not belong in the task. A public download is not automatically permitted, safe, or useful for your purpose.

Hugging Face Datasets is the main discovery route because a repository can include a dataset card, revision history, files, and discussion with the data. Use the dataset viewer for a first look, then read the repository material and pin the revision you actually use.

Kaggle is a second useful discovery route. Read the description, license, publisher, update history, files, and discussion before you use a dataset. Neither service gives you ownership or permission for your intended use.

Read the demonstration as an operator

The instructor runs the job while you follow the evidence in order. Each stage proves one part of the final decision. If a link in that chain is missing, the claim has to become narrower.

Stage 01 · State the behavior claim

The demonstration tests one behavior from a small public dataset. Before any training starts, the instructor states the task, response form, acceptance check, and non-goal. The purpose is to test a narrow behavior, not to claim that the model has generally improved.

  1. Write this statement: “Given [input], the adapter returns [output]. It passes when [check]. It is not evaluated for [non-goal].” If you cannot complete it, the behavior is not ready for training.

Stage 02 · Admit public data

The instructor takes a small seeded sample from public HuggingFaceH4/ultrachat_200k and keeps a separately sampled held-out set outside the training input. The split happens before fitting, so the evaluation cases cannot quietly become examples for the adapter to memorize.

The dataset card declares an MIT license and provides conversational messages records. That does not remove the review step. The instructor pins the revision, reads the card and sample rows, and records the split rule in the private dataset admission record.

This is a method demonstration, not a claim that the resulting adapter is safe or useful for general chat.

  1. Keep the dataset URL and revision, license or terms, sample rows, behavior, data boundary, and held-out split. The held-out split stays outside training.

Stage 03 · Save the base-model control

Before training, the instructor runs the base model on the held-out suite and saves its raw outputs. The base model and adapter will use the same cases, prompt wrapper, generation settings, and evaluator. This baseline is the control that lets you tell a real improvement from a good-looking result.

  1. Record the base model and revision, prompt or chat template, decoding settings, time, held-out cases, raw outputs, scores, and the failure type for each miss.

Stage 04 · Start a bounded private Job

The instructor uses a private Hugging Face account with paid GPU compute. A Hugging Face Job runs a command on selected remote hardware and exposes status and logs, which makes it a useful unit for a bounded training run.

Before launch, the instructor selects the current GPU flavor and an explicit timeout, then confirms that the output repository is private. Tokens live in platform-managed secrets, never in code, notebook cells, run records, or shell history.

The training script uses supervised fine-tuning tooling and PEFT. Conversational data must use the expected messages or prompt/completion form so that the trainer can apply the model’s chat template. Render a few examples before the run: check the role order, assistant targets, special tokens, and truncation. A successful training job can still teach the wrong token sequence.

The run record carries the details someone else needs to understand the result: model and dataset revisions, chat template, adapter setup, sequence limit, batch plan, learning rate, step or epoch limit, seed, environment, Job ID, hardware, timing, and stop condition.

  1. A Job log is not enough. Keep a run record with the data and model revisions, configuration, environment, compute, timing, private output, and stop condition. No secret belongs in that record.

Stage 05 · Read the run data

Loss and throughput can help you spot an interruption, memory limit, or implausible configuration. They do not settle the question the lesson asks. A low loss can coexist with leakage, memorization, poor task fit, or damage to related behavior.

Use memory-saving features to make a valid run smaller, not to hide a weak experiment. QLoRA can reduce base-model memory pressure. SFTTrainer can pack short examples into the same training sequence when the format and masking rules make that appropriate. For conversational data, verify that only the intended assistant text contributes to loss. These are efficiency controls, not quality controls.

Save a checkpoint when it gives you a real recovery point. Then move to the held-out suite, where the adapter has to perform on work it did not train on.

Stage 06 · Score unseen cases and decide

The instructor loads the adapter with the base model and reruns the held-out suite. The evaluator uses the original check, and the raw output is kept for both model states. Now the base model and adapter can be compared without coaching either one.

Use more than one kind of case. Keep realistic in-domain cases, edge cases, format-following cases, and examples the base model already handles well. When a human can judge the output, review the comparison without showing which answer came from the base model or adapter first.

Read every change in the table. An improvement may be useful, and a hold may be expected. A degradation needs a cause before the adapter moves into other work.

  1. Use one row for each case, with the base score, adapter score, raw-output paths, failure type, and totals. Keep the model revision, chat template, prompt wrapper, decoding settings, and scorer fixed. A lower loss does not meet this check.
  2. State the supported use, out-of-scope work, evidence count, owner, next review, and return path to the base model. The adapter stays private unless release review approves a different state.

Linux: local CUDA path

Linux with a supported NVIDIA GPU is the most direct local path. Before training, confirm the driver, GPU visibility, free VRAM, disk space for models and checkpoints, and an isolated Python environment. Those checks tell you whether the machine can run the job you are about to ask of it.

  1. Create separate data/, eval/, configs/, runs/, and artifacts/ directories.
  2. Keep tokens outside the project, and do not commit outputs without a reviewed policy.
  3. Convert the admitted data to the trainer input format, then keep the source and conversion record.
  4. Run a small smoke job and record memory use, throughput, checkpoints, and any exact error.
  5. Run the bounded LoRA or QLoRA configuration, then save the adapter and configuration apart from the base model.
  6. Score the base model and adapter on the held-out suite before you make a use claim.

Tools to assess: Unsloth provides a current local training path. Axolotl is useful when you need a versioned YAML configuration or expect later multi-GPU work. Their support and install paths change, so check the current documentation before you set up either tool.

macOS: Apple Silicon path

An Apple Silicon Mac is useful for data work, inspection, inference, and small compatible tuning tests. Check unified-memory pressure and free disk space before you load a model. Unified memory is not interchangeable with NVIDIA VRAM, so use a short smoke run to learn what your specific Mac can sustain.

  1. Carry over the behavior contract, data record, split files, baseline suite, and run record.
  2. Select an MLX-compatible base model and read the current MLX LM LoRA guidance.
  3. Run a short smoke job, then record memory pressure, throughput, output location, and conversion steps.
  4. Score the adapter on the same held-out suite you used for the base model.
  5. Move the unchanged project to cloud GPU compute if the Mac swaps heavily or cannot meet the required scope.

Current reference: MLX LM supports low-rank fine-tuning on Apple Silicon for compatible models. Its model formats and commands change over time, so use the current LoRA guide when you run.

Hugging Face: private instructor Job

Use Hugging Face when you want managed GPU compute, Hub-native data, logs, and private artifacts in one place. The instructor demonstration is the reference path. Learners inspect the evidence from that run, so they do not need paid access to participate.

At inference time, keep the adapter separate from the base model until you have a measured reason to merge it. A separate adapter is easier to version, compare, roll back, and scope to one workload. If a later serving stack requires a merged model, retain the original adapter, exact base-model revision, merge procedure, and post-merge evaluation results.

Write the inference contract beside the adapter: the tokenizer and chat template, system prompt, generation defaults, stop conditions, structured-output checks, and safety behavior. A tuned adapter can look broken when the serving path uses a different template or decoding setup from the one used in evaluation.

RunPod: persistent Pod

Use RunPod when you need an interactive remote Linux GPU, a specific accelerator, or a persistent workspace. A Pod gives you a terminal, but that alone does not make the work repeatable. Keep the project, image, data revision, configuration, and artifact locations explicit from the start.

  1. Use the current Pod selection guidance to choose VRAM, disk, region, policy fit, and run length. Do not choose only by hourly price.
  2. Attach persistent storage before you download a model or start a run, then keep data, configuration, checkpoints, logs, and adapters in known persistent locations.
  3. Record the image or template and the storage location that the run uses. A Pod-specific volume can persist through a stop but can be removed when the Pod is terminated; copy required artifacts to durable storage before termination.
  4. Use current RunPod secret guidance for tokens. A token does not belong in a notebook, command history, dataset, configuration, or committed file.
  5. Run the same smoke job and bounded configuration that you would use locally, then monitor disk, GPU memory, logs, checkpoints, and spend.
  6. Verify the adapter, run record, configuration, evaluation report, and model card in persistent storage before you stop compute.
  7. Use current Pod management guidance to stop or terminate the Pod. A completed training command does not stop billing by itself.

Before any serving step, run the adapter through the same task-specific evaluation and a small operational smoke set. Verify the chat template, prompt wrapper, structured-output checks, long-context behavior where it matters, refusal behavior, and rollback behavior in the serving path. A successful notebook inference does not prove that a deployed endpoint has the same behavior.

  1. Name the compute choice, private artifact storage, secret method, budget and time limit, checkpoint location, evaluation location, and stop or termination action.

Lesson outcomes

Check an outcome only when you can point to its evidence. Watching a GPU run is useful context, but it does not establish the result.

  1. The record names the input, output, acceptance check, and non-goal. It explains why fine-tuning is the next test instead of retrieval, a tool, prompting, or validation.
  2. The record identifies the source and revision, rights, sample contents, risks, conversion, rendered template, and rules for the training, validation, and held-out splits.
  3. The record includes base raw outputs and scores for held-out cases, as well as the model, prompt or template, and decoding conditions.
  4. The run record identifies the model, data revision, adapter configuration, environment, compute, time and budget limits, output, checkpoint, stop condition, and secret method.
  5. The comparison uses the same held-out suite and score rule for the base model and adapter. Training loss alone does not meet this outcome.
  6. The decision states fit, not-fit, limits, evidence, owner, review date, visibility, inference contract, and the return path to the base model.
  7. The scope matches the operating system, accelerator, usable memory, model class, context, and work type.
  8. The plan identifies private artifacts, secrets, storage, compute, budget and time limit, evaluation, recovery, and shutdown.

Before you move on

Keep one behavior contract and one dataset admission record from this session. When you run an adapter later, begin only after the base-model baseline, data boundary, held-out cases, and rollback path are ready.

If you get stuck

  • The task changes often. Fine-tuning will preserve yesterday’s behavior while the target keeps moving. Stabilize the task, instructions, or retrieval path first.
  • The dataset card does not establish permission or provenance. Reject the dataset or find a source that does. Missing evidence is a stop condition, not a gap to explain away.
  • The run uses too much memory. Save the exact error and configuration. Then reduce model size, sequence length, or batch plan; use QLoRA where supported; or move the unchanged project to cloud GPU compute.
  • Loss decreases but held-out scores do not improve. Keep the base model, then inspect data quality, split leakage, task fit, evaluator quality, template mismatch, and whether fine-tuning was the right control method.
  • The adapter passes in a notebook but fails when served. Compare the tokenizer, chat template, system prompt, generation defaults, quantization, and adapter-loading path. Treat the serving path as a separate evaluation target.
  • The cloud run ends but artifacts are missing. Do not stop compute until the checkpoint, adapter, configuration, logs, and evaluation evidence are verified in persistent private storage.
  • You want to publish the adapter. Stop for release review. Confirm the base-model license, data rights, policy approval, model card, evaluation limits, and removal path first.
