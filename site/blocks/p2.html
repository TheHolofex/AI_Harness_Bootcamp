Build one useful local system

The supplied packet looks like real project work: a charter, a deliverable list, dependency notes, decisions, status updates, and a source register. The facts are spread across formats. By the end of P2, one local board shows what is ready, what is blocked, what decision is needed, and which source supports each item.

You direct the build with six complete prompts. Codex writes and tests the SQLite, MCP, skill, agent, plugin, renderer, and hook code. You inspect the evidence and make the release decision; you do not hand-author Python, TOML, JSON, or SQL.

The three files you release

  • PROJECT_BOARD.html — the visual board a lead can use at a glance
  • PROJECT_STATE.json — the board's structured, source-linked state
  • RUN_RECEIPT.json — the release check, hashes, labeled measured/reported run facts, and PASS or HOLD result

Before you start

  • Complete the Harness Control Plane presentation immediately before this module
  • Use GPT-5.6 Terra for the main chat and all three custom agents
  • Keep Ask for approval selected. Approve only project-local build and test commands named in the prompt
  • No external account or cloud document is required. The database, MCP server, plugin, and board stay on this computer

The system you are building

Messy project files → SQLite ledger → four read-only MCP tools → skill + two workers → visual board → sequential review → deterministic release hook.

One writer Two workers inspect separate parts of the project in parallel. The main thread alone invokes the deterministic renderer. The reviewer runs after the board exists and never edits it.
No invented project state Missing or conflicting information stays visible as unknown or needs-decision. A polished guess is a database error with better typography.
Before lunch · Harness case talk (45 min) The lead shows a real personalized harness in use: the job, component choices, evidence, operating cost, and decisions that remain human.
1 · NormalizeSQLite ledger

Stable records, relationships, source identity, explicit unknowns, and a deterministic rebuild.

2 · ExposeLocal MCP

Four decision-sized, read-only questions instead of broad database access.

3 · OrchestrateSkill + agents

Two parallel inspections, one write-capable main thread, and one sequential reviewer.

4 · ReleaseBoard + receipt

A visual operating picture and a deterministic check of the saved artifacts.

Each layer removes a real bottleneck

The organizer is useful because the layers work as one line. None of them is present merely to demonstrate a feature.

LayerJob in this systemImportant boundary
Source packetHolds the facts as received, including gaps and conflictsNever rewrite a source to make the board cleaner
SQLite ledgerNormalizes projects, deliverables, dependencies, decisions, updates, and sources onceEvery material record keeps its source identity; unknown stays unknown
Local MCPAnswers four recurring project questions through a small read-only tool surfaceNo arbitrary SQL, writes, network listener, or silent fallback to model memory
SkillCarries the repeatable organizer workflow and stop conditionsOne focused workflow, not another always-on policy manual
SubagentsInspect scope/state and dependency/ready-work in parallel; review after assemblyRead-only roles on Terra; the main thread alone invokes the renderer
PluginPackages the stable skill, renderer, and one release hookInspect before installing; trust the exact hook separately
Release hookChecks the real saved board, state, ledger, and contract when the renderer creates the release setIt proves checks ran; it does not choose priorities or approve a decision
Data designCompile facts before asking for judgment

The model should not reread six files and reconstruct relationships differently on every question. Build the ledger once, verify it, then query it.

Tool designExpose questions, not machinery

get_ready_work is a useful contract. An unrestricted “run SQL” tool widens risk and pushes schema trivia into every turn.

Agent designParallelize independent reads

Scope and dependencies can be inspected together. Review must wait for the candidate because reviewing a board that does not exist saves no time.

Release designSeparate correctness from judgment

The gate can verify structure, provenance, consistency, and hashes. A person still owns priority, escalation, and the decision to act.

- schema.sql
- build_project_ledger.py
- verify_project_ledger.py
- project_ledger.sqlite3

Requirements:
- Use Python's standard-library sqlite3 only for the database layer.
- Create exactly these domain tables: projects, deliverables, dependencies,
  decisions, updates, and sources. Use stable ids, declared foreign keys, useful
  indexes, and source identity on every material record.
- Use parameterized SQL for values, enable foreign-key checks, use transactions,

  "Not assigned in source" literally; it is an honest unknown, not SQL NULL or a

- dependencies: @modelcontextprotocol/server 2.0.0 and zod 4.4.3;
- devDependencies: @modelcontextprotocol/client 2.0.0.
Use exact versions with no caret, tilde, tag, or other range. Let the SDK
negotiate the protocol with Codex. Do not hand-roll JSON-RPC framing, pin a
remembered protocol version, open a network listener, or add a cloud service.

Expose exactly four tools:
- get_project_snapshot: project identity, delivery state, source coverage, and
  explicit unknowns—do not duplicate the path, blocked-work array, or decision
  queue owned by the other tools;
- get_ready_work: deliverables whose declared dependencies are satisfied, with
  readiness_evidence that names the dependency, predecessor and its status, and
  both source IDs;
- get_dependency_path: the longest declared launch path for a named deliverable;
  the packet has no durations, so describe only its declared relationship sequence;
- get_decision_queue: open decisions, options/status if supplied, owner if
  supplied, and affected work.

Every tool must open project_ledger.sqlite3 in read-only mode, use parameterized
queries, return stable ids and source ids, distinguish empty results from errors,

- plugins/project-organizer/mcp/server.mjs;
- plugins/project-organizer/mcp/query_ledger.py, the bounded read-only SQLite

Define no install-time lifecycle scripts such as preinstall, install,

test commands; dependency installation must never execute package scripts.

Operating notes for a real local utility

These are the design choices worth carrying into your own project organizer, tracker, intake queue, or operating dashboard.

Keep the ledger trustworthy

PracticeWhy it mattersRelease evidence
Stable ids and declared foreign keysRelationships survive file order, display changes, and repeated buildsForeign-key verification and orphan count
Source identity on material recordsA lead can trace the board instead of trusting generated phrasingSource ids in MCP results, state, and board
Explicit unknownsThe system does not turn missing ownership, dates, or decisions into invented factsThe board preserves source language such as Not assigned in source
Temporary build plus atomic replacementA failed rebuild cannot leave a half-written live databaseVerifier passes before the target is replaced
Parameterized queriesData values stay data, and inputs cannot reshape the queryTests exercise real and empty inputs

Keep MCP smaller than the database

BoundaryWorking rule
Tool surfaceExpose the four questions the organizer needs, not arbitrary SQL or table dumps
PermissionsOpen the database read-only and omit mutation tools; annotations help the client but do not replace enforcement
ProvenanceReturn stable record and source IDs plus the same source fingerprint from every tool so later layers cannot join different source states
FreshnessRun the bundled data-only verifier on every request; exact schema, source hashes, and source-row parity must pass before a tool answers
ErrorsDistinguish no matching work from a missing, stale, or invalid ledger; never answer from memory when the tool fails
ProtocolUse the current SDK's negotiation and schemas; do not hard-code a protocol snapshot into lesson logic
StateTreat tool calls as stateless; derive every answer from the current verified ledger rather than server-process memory
ShutdownKeep the local server bound to stdio, with no listener or background service to remember after class

Keep orchestration proportional to the work

  • An MCP call returns no provenance. Stop the run and repair the tool contract. Do not let the next layer reconstruct source identity.
  • The plugin does not appear. Confirm .agents\plugins\marketplace.json and plugins\project-organizer exist. Run codex plugin marketplace list; if the P2 project root is absent, add it with codex plugin marketplace add "$env:USERPROFILE\Documents\HarnessBootcamp\P2_Project_Organizer".   • You need source-package diagnosis. Only for instructor testing or hook recovery, ask Codex to run py -3 plugins\project-organizer\hooks\release_gate.py --check. The command does not write the receipt, release files, evidence, or repair count. A PASS checks the learner source package; it does not prove the installed hook copy is current or that Stop released the board.

If plugin code changes, validate it, remove/add the plugin, restart, review and trust /hooks, then run the normal Stop path.
