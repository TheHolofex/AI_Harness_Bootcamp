What this is worth at work

Task Group MERIDIAN runs six desks out of Station Halberd. A tranche of people is arriving between 14 and 22 August. Once they land there are 52 people on station and 33 of them are new. Somebody has to say, for each one, what they can actually do — and then make sure the right messages reach them.

The material for that job is already on the desk, and it is a mess. Four files claim to be the arriving roster. No two of them agree on column names, field order, or how a date is written. One is a spreadsheet with two title lines above the header. One is a chat paste with no columns at all. One is a system export whose keys changed in an upgrade. One is a partner sheet that did not survive being exported, and it is the dangerous one: it reads clean and quietly loses a person.

What people can do is written down in exactly two records — a billet catalog and a qualification register. It is not written down in the desk they report to, or in what somebody said on the phone. Five distribution lists carry the traffic, all kept by hand, and they have drifted: two names on them belong to nobody, one belongs to a person who left on 6 August, and several people who earned a place are not on any list.

You build the machinery that takes this apart and puts it back together on demand: one shape at the door, one capability map with its evidence attached, five lists generated from that map, and two rules that run whether anybody remembers them or not.

What you leave with

  • A normalizer behind a hook, so no arriving file reaches the model in its original shape and a damaged file is refused rather than half-read
  • A skill that maps people to capabilities and says unknown where the records do not say
  • A skill that generates all five distribution lists, so updating them stops being an editing job
  • A hook that blocks any line in a list that cannot name the record that put it there
  • Both narrowed until they leave unrelated material alone
  • One package carrying the lot, checked for paths and secrets that would not travel

Four arriving formats → normalize at the door → capability map with evidence → five generated lists → source gate → one installable package.

The ideas doing the work

Five ideas carry this work. Read them once now, and come back when a result surprises you — the reason will be one of these.

Convert once, at the door

You have four sources for one fact set. If you leave them in their own shapes, every step downstream has to know about all four: the date parser has to handle 14 AUG 26 and the 18th and an ISO-8601 timestamp; the name reader has to know that one file splits last and first while another writes Ashworth, D. in running text. That knowledge spreads, and it rots at different rates in different places.

Converting at the door means one component knows about the four shapes and everything after it knows about one. When a fifth format turns up — and it will — you change one component. The cost of that choice is that the shape has to be honest: it needs a slot for every fact any source carries, and it must be able to say this source did not carry that. A normalizer that fills a blank column to keep its output tidy has moved the mess downstream and hidden it on the way.

A parse that does not crash is not a parse that worked

The partner roster is a spreadsheet that broke during export. It does not raise an error. Python's CSV reader takes it, returns eight rows for the eight people it names, and reports nothing wrong. The damage only shows when you count identifiers instead of rows. One cell on the first data row opens a quote and never closes it, so the reader carries that cell straight across the line break and the whole of the next person's record lands as extra fields tacked onto the first row — their name buried in a remarks column, their identifier P-4902 in a column that has no name. A later row has its fields in a different order, so a billet code lands in the identifier column and P-4904 never reaches it at all — and because the header names two columns the same thing, a reader that keys on names writes that identifier into a name field and then overwrites it. Eight rows, eight people, and only six of the eight identifiers anywhere in the column that is supposed to hold them. Nobody is told.

This is why "did it throw?" is a weak check. A check that only catches exceptions will pass this file, and the run will report success on a roster that is missing two people. The checks that catch it are ones that assert something about the shape you expected: the header has a duplicate column name, and duplicate names cannot key a record; the file holds an odd number of quote characters, so one of them is unclosed; several rows carry a different number of fields than the header declares; the date column holds #REF! in two rows and bare numbers like 45892 in two others; the file ends mid-value with no closing newline; and the identifiers that reach the identifier column do not account for the identifiers sitting in the raw bytes. Any one of those is enough to refuse the file. You do not need to know which one broke it to know it is broken.

Notice which check does not work: counting rows. Eight rows come back for eight people, so a row count matches and tells you nothing. The count has to be of identifiers, in the column meant to carry them. A check that compares two numbers which both come out of the same broken parse is not a check.

Refusing is the correct outcome here. The alternative — take the eight rows and carry on — puts two people on no list at all and produces no signal that it happened.

Capability is written down in two places, and a desk is not one of them

The group recognises six capabilities: SIGNALS, MOVEMENT, MEDICAL, SUPPLY, IMAGERY, LIAISON. A person holds one of them by billet — the post they fill, listed in the billet catalog with its capability — or by qualification — a certificate in the register, granted by a desk, with a status of current, expired or pending. That is the whole list of things that count as evidence.

Three things look like evidence and are not. A gaining desk is an address, not a trade: the desk directory says so outright, and the catalog proves it — one billet sits on the Movement desk and carries IMAGERY, another sits on the Signals desk and carries SUPPLY. Free text in the chat paste is hearsay, and the person who typed it says so in the file: treat the trades as hearsay until somebody checks the register. An expired or pending qualification is a record of something that is not currently true.

Two billet codes in the arriving manifest are not in the catalog at all. The catalog is revised quarterly, so a post stood up since the last revision has no entry yet. That is a real unknown with a known cause, and the right output is to say so — not to guess from the code's prefix.

Generated, not edited

The five lists on the desk today are hand-maintained, and you can read their history in their contents. Somebody was asked to add a name and did, without a record behind it. Somebody left and nobody took them off. Somebody who sits at the Signals desk got added to the Signals recall list even though what they actually do is run the stores. Each of those was one small reasonable act, and together they produced lists that nobody can now defend.

Generating the lists from the map every time changes what maintenance means. You no longer edit a list; you correct a record, and rerun. The property that makes this worth the trouble is that a change is bounded: change one person's qualification status, rerun, and only the lists that should move do. If a small change moves everything, the generator is reading something it should not.

The cost is real and worth stating. A generated list cannot be quickly patched at the desk, and the first time somebody genuinely needs a name on a list before the record catches up, they will feel that. The answer is to fix the record, not to reopen the file — but it is a slower answer, and that is the trade you are making.

Advice, and code that runs anyway

A skill is a procedure the model loads when the work matches its description. It is good at judgment that changes with the case: which record grants this capability, what to do with a person the records cannot place. It is advice, and advice can be skipped — by a model that did not load it, by a person in a hurry, by a run that took a different route.

A hook is a command that runs at a fixed point in the run whether anybody wanted it to or not. It is good at one thing: a rule that must hold every time and can be decided by looking at the material. "Nothing reads a raw arrivals file" is that kind of rule. "Work out whether this person's qualification counts" is not — there is no fixed answer to check against.

The test for which one you are building: ask what happens if nothing reads your instruction. If the answer is "then the rule does not hold," it is not a rule yet, and it belongs in a hook.

What counts as a source is your call, and it has teeth. If you accept "a desk head asked for it" as a source, this hook stops catching the case it was built for. If you accept only the two capability records, you have to decide what happens the day somebody genuinely needs to be reachable before their paperwork lands — an answer exists, but it is a record, not an edit.

When it does not fire. If nothing was refused, check three things in order: does /hooks show the hook as trusted, does the matcher include the tool that actually wrote the file, and did the chat write through the shell instead. This is not a gap to plug with a second hook: what actually protects you is that the list is generated, so an edit made outside the harness survives only until the next rerun and can never reach a record. Enforcement always has an edge. Being able to say where yours is worth more than believing it does not have one, because the rule you think covers everything is the one nobody checks.

Stage 06 · Find out why something did not fire

Something is about to stop working, and it will not tell you. Nothing happening looks the same whether a component never loaded, ran and found nothing, or was never reached at all. Before you change a line, find out which of the three it was.

Run this in PowerShell:

cd "$env:USERPROFILE\Documents\HarnessBootcamp\P2_Inbound"
Move-Item -LiteralPath "inbound\arrivals\arrivals_c_persys_export.json" -Destination "held\arrivals_c_persys_export_v1.json" -Force
Copy-Item -LiteralPath "held\arrivals_c_persys_export_v2.json" -Destination "inbound\arrivals\arrivals_c_persys_export.json" -Force
py -3 scripts\normalize_arrivals.py --source inbound\arrivals --out normalized\arrivals.csv

The system that produced that export was upgraded, and this is what it sends now. The same eleven people plus one more, from the same system, arriving in the same place, under the same name. The run does not fail. There is no error and no warning.

Work out which of the three it was before you touch anything:

  1. Did it load? In the integrated terminal, run codex and use /skills and /hooks. A skill that is not listed never loaded. A hook shown as untrusted was skipped, and a hook you edited since Stage 04 will be sitting there waiting for review
  2. Did it run? Open normalized\intake_receipt.json and find the entry for the export. No entry at all means nothing claimed the file. An entry names the handler that did
  3. Was it reached? Read records_read and records_emitted on that entry, against identifiers_in_bytes. Read 0 and emitted 0 means the handler ran and found nothing to read. Read some and emitted none means it read records and dropped them. Those are different faults and the receipt is what separates them

Write down which of the three it was, and the field in the receipt you decided it on, before you look at the file.

Now open the file and confirm it:

  1. Open inbound\arrivals\arrivals_c_persys_export.json and held\arrivals_c_persys_export_v1.json side by side
  2. The records are no longer under personnel. Every field key changed as well. The date is no longer an ISO-8601 string
  3. A reader that asks for personnel and gets nothing returns an empty list. That is not an error to Python and it was not an error to your normalizer. The receipt is where it shows: a handler claimed the file, read 0 records, emitted 0 — with 12 identifiers sitting in the bytes

The fix is one line of judgment, not a rewrite. Either the reader accepts both shapes, or it refuses a JSON export whose top-level record collection it does not recognise. Both are defensible; silently returning zero rows is not. Whichever you choose, make the check that already exists apply here: the normalizer requires every identifier in the raw bytes to reach a parsed record for CSV — hold JSON to the same rule, and 0 placed against 12 in the bytes becomes a refusal instead of a shrug.

What you should see afterwards. 12 people from the upgraded export, 34 in the output file, and a refusal if you point it at a JSON file whose shape it does not know. Then put the original back:

Move-Item -LiteralPath "held\arrivals_c_persys_export_v1.json" -Destination "inbound\arrivals\arrivals_c_persys_export.json" -Force

Questions worth arguing about

None of these has one right answer. Each one changes what you build, so it is worth having the argument before somebody has to live with your choice.

  • The partner file names eight people and yields seven records. Refusing loses all eight. Is that right? The case for refusing: seven silently is worse than none loudly, because seven produces no signal and somebody has to notice the gap on their own. The case against: a person who is genuinely arriving is now on no list at all, and "we refused the file" is a poor answer at the gate. Both positions accept the same thing — the file has to be re-cut. They differ on who carries the risk in the meantime.
  • Somebody is covering nights for the aid station and is on no record. What reaches them? If your source rule is strict they get nothing, and a real person doing real work stops getting recalled. If you loosen it, the ghost on the imagery list comes back. The interesting answer is neither: it is that the fix is a record, and the question is how fast you can get one made.
  • A gaining desk is not a trade — but should the lists be built on capability or on desk? Capability is what the directives ask for, and it is what the records support. Desk is what people actually check, and it is how the room is laid out. Building on capability means a person at the Signals desk does not get the Signals recall, and somebody will find that surprising every single time.
  • The badging direction covers every arrival regardless of trade. Which list is that? It is not a capability list, so it does not fit the five. Do you add a sixth list keyed on report date, or is a message with no list behind it a different kind of thing? Whichever you choose, notice that the answer decides what happens to the eight people your map could not place.
  • Should the source gate block, or mark and continue? Blocking is honest and it stops the drift, and it is also the thing people disable at 5pm on a Friday. Marking preserves the record of what was untraceable and lets the list go out. A gate that has been switched off enforces nothing, so the question is really: which version survives contact with a bad week?
  • What is a good enough reason to skip the normalizer? If there is one, the hook should encode it. If there is not, say so plainly — because the exception people actually use is the one nobody wrote down.

If you get stuck

  • py -3 is not recognized. Return to the install clinic and repair the Python launcher. Do not work around it by changing a script.
  • Codex cannot see inbound. The app works from the folder the project is opened at. Check that it is P2_Inbound and not the course repository or your Documents folder.
  • The partner file produced rows. The integrity checks are too weak. The check that catches it compares how many records the reader returned against how many person identifiers are in the raw bytes. Add that one first.
  • A hook does not fire. Check in this order: /hooks shows it and shows it trusted; the matcher names the tool that actually did the work; the event is the one that happens at that moment. A hook you edited is untrusted again until you re-trust it, and an untrusted hook is skipped in silence.
  • A hook fires on everything. Do not remove it — narrow it. Widen the condition it lets through, one clause at a time, and rerun the whole set after each change so you can see what the clause cost.
  • The capability skill does not load. The description is what decides. Put the trigger material in it — a normalized arrivals roster, capability, billet, qualification — and name what it is not for. A description that reads like a title never fires.
  • A count is wrong and you cannot see why. Take one person and walk it: the raw line, the normalized row, the map row, the list. The step where the person stops being right is the step to fix. Reading the whole output again will not tell you.
  • You edited a file under inbound\ and want it back. Recopy that one file from the course repository with Copy-Item. Do not repair the material to make a check pass.
